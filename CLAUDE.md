# Timeline

Трекер участия в хакатонах: администратор заводит хакатон, назначает участников и
настраивает напоминания; участник видит свои назначения и сам отмечает, что
зарегистрировался. Напоминания уходят в Telegram или на email.

**Ключевая оговорка ТЗ:** система не проверяет внешний сайт регистрации. Статус
регистрации — самоотчёт пользователя либо административно установленное состояние,
а не подтверждённый факт. Не добавляйте логику, которая делает вид, что статус
проверен.

Архитектура: модульный монолит на Go, PostgreSQL, REST/JSON API, React SPA,
отдельный процесс worker/scheduler для доставки уведомлений.

## Структура

```
backend/     Go: cmd, internal/{config,models,services,adapters,controllers,cli}, migrations
frontend/    React + TypeScript + Vite, Tailwind + shadcn/ui, TanStack Query, react-router
deploy/      Dockerfile backend и frontend, nginx.conf, docker-compose.yml (+ .dev.yml)
docs/        ТЗ, backlog, порядок реализации, соглашения API, OpenAPI
Makefile     Команды разработки монорепозитория
```

Оба Dockerfile многостадийные: стадия `runtime` собирается по умолчанию и идёт
в боевой режим, стадия `dev` используется только оверлеем
`deploy/docker-compose.dev.yml`.

Внутри backend слои разделены строго: `controllers` знают про HTTP,
`services` содержат доменные правила и транзакционные границы,
`adapters/repositories` — SQL поверх pgx, `models` — типы домена и ошибки.
Контроллер не ходит в репозиторий напрямую.

Frontend организован по модулям предметной области (`src/modules/*`), общий код —
в `src/shared` (`api`, `ui`, `lib`), оболочка и маршруты — в `src/app`.

## Запуск

Приложение работает только в контейнерах: Go, Node и PostgreSQL на машине для
запуска не нужны.

```bash
make docker-up     # боевой режим: nginx с production-сборкой фронтенда
make dev           # режим разработки: HMR у фронтенда, go run у backend
make dev-restart   # перекомпилировать и перезапустить backend
make docker-down   # остановить стек (том с данными сохраняется)
```

Оба режима поднимают один и тот же состав: postgres → миграции → создание
первого администратора → API → worker → фронтенд. Отличается только последняя
пара: в боевом режиме nginx раздаёт собранный SPA и проксирует `/api` и `/docs`
на API, в режиме разработки dev-сервер Vite отдаёт SPA с HMR и проксирует
`/api` сам. Исходники в режиме разработки смонтированы в контейнеры: правки
фронтенда подхватываются сразу, backend перекомпилируется по `make dev-restart`.

По умолчанию: приложение на `http://localhost:5173`, API на `http://localhost:8080`,
Swagger UI на `/docs/`, вход `admin@example.com` / `password123`.
Порты переопределяются переменными:
`make docker-up WEB_PORT=5199 API_PORT=8099 POSTGRES_PORT=5433`.

Конфигурация приложения — только переменные окружения (`backend/internal/config`),
файлы `.env` приложением не читаются. `backend/.env.example` — полный список
параметров из приложения C ТЗ; `make docker-up` создаёт из него `backend/.env`,
который compose передаёт контейнерам.

## Проверки

```bash
make verify        # контракт, типы, линтер и тесты обеих частей
make back-test     # go test ./...
make test          # vitest
make test-contract # контрактные тесты против настоящего API в контейнере
make e2e           # вход в настоящем браузере против того же стека
make lint          # biome
```

`make verify` должен проходить до того, как задача считается сделанной. В
отличие от запуска приложения, проверки выполняются на машине и требуют
установленных Go и Node; в CI выполняются те же команды.

## Правила работы

**Задача не закрыта, пока нет миграции или изменения OpenAPI, тестов её
приёмочных сценариев и прохождения всех уже завершённых сценариев.** Следующую
задачу нельзя начинать только потому, что предыдущая сгенерировала код: сначала
должны проходить сборка, линтеры и релевантные тесты (dependency-order, раздел 5).

**Контракт пишется до реализации.** Endpoint сначала описывается в OpenAPI, потом
реализуется — тогда frontend и backend идут параллельно от общего контракта.

**Изменение API.** Аннотации swag живут рядом с кодом контроллеров и в
`backend/internal/controllers/router.go`. После изменения:

```bash
make back-docs   # пересобрать swagger.yaml/json и опубликовать в docs/
make types       # перегенерировать frontend/src/shared/api/types.gen.ts
```

`make types-check` в CI ловит расхождение типов и контракта. Файлы `*.gen.*`
руками не правятся.

**Миграции** только вперёд, парой `NNNNNN_name.up.sql` / `.down.sql` в
`backend/migrations`. Существующие применённые миграции не редактируются.
Правила, которые обычный `CHECK` выразить не может, решены явными приёмами и
менять их походя нельзя: `registration.deadline_at <= event.end_at` — через
денормализованный `event_end_at` в той же строке, «не больше 10 правил на
Registration» — через нумерованные слоты `slot_no` и сервисный слой,
неизменяемость `audit_log` и запрет удаления `notifications` — через триггеры.

**Язык.** Код — на английском: имена, строковые константы, сообщения `slog`,
машинные коды ошибок, тексты миграций. Русский существует только в JSON-словарях
локализации и в `docs/`. Продуктовые тексты и уведомления приходят пользователю
на его языке, но живут в словаре, а не литералом в коде.

Ошибки API: `code` — стабильный английский идентификатор, `message` —
английский запасной вариант, текст на экране клиент берёт из словаря по коду.
Сервер язык клиента не угадывает.

**Комментариев нет вообще** — ни строчных, ни блочных, ни docstring. Русский
комментарий не переводится на английский, а удаляется.

**Русский язык живёт ровно в двух местах: `docs/` и JSON-словари локализации.**
Больше нигде. Это касается и того, что кодом не является: `Makefile`, CI,
`.golangci.yml`, `docker-compose`, `Dockerfile`, `nginx.conf`, скрипты,
корневой `README.md` и этот файл. Комментарии в конфигурационных файлах
допустимы, но пишутся по-английски.

**Git.** Коммиты разрешены и делаются после завершения связанной порции
работы. Сообщение — одна осмысленная строка `type: description` **на
английском** (`feat`, `fix`, `docs`, `build`, `chore`, `refactor`, `test`),
без тела и без соавторства.

**Запрещено:** `push`, `stash`, `checkout`, `restore`, `reset`, создание и
переключение веток. Push делает владелец сам. `stash` и `restore` опасны
особенно: в дереве может работать другой агент, и его правки исчезнут молча.

Подчинённым агентам git-операции не поручаются — коммит делает координатор
после проверки результата.

Подробности и замер текущего состояния — часть III2
[плана рефакторинга](docs/refactoring.md).

## Что стоит помнить

* **Cookie и CSRF.** Сессия — `HttpOnly` cookie (`access_token` 15 минут,
  `refresh_token` 30 дней с ротацией). Любой изменяющий запрос обязан нести
  `X-CSRF-Token`, совпадающий с cookie `csrf_token`; токен ротируется, поэтому
  клиент перечитывает его из cookie после ответа. Поэтому же SPA и API держатся
  на одном origin (vite proxy в разработке, nginx в Docker) — иначе понадобились
  бы CORS с credentials и `SameSite=None`.
* **403 против 404.** Объект существует, но роль не даёт доступа — `403`. Объект
  чужой и сам факт его существования раскрывать нельзя — `404`.
* **Batch-операции** возвращают `200` даже при частичных отказах, каждый элемент
  обрабатывается своей транзакцией, результат — построчный.
* **Дедупликация уведомлений** держится на версионируемом `logical_key`. Прежде
  чем трогать scheduler, worker или правила, перечитайте раздел 9 ТЗ и сценарии
  AC-NOTIF-01…19: там описаны конкурентный scheduler, отмена во время отправки,
  fallback канала, retry и восстановление после падения.
* **Моков нет.** Платформа ходит в настоящий backend и в разработке тоже.
  Единственное место подставных данных — тесты: фикстуры и поднятый в
  контейнере настоящий API (`make test-contract`, `make e2e`). Подделок нет
  ни на фронтенде, ни в backend, ни в базе.
* **Тесты — слабое место.** Сейчас в репозитории только точечные проверки
  (ограничения БД, rate limiting, контракт и вход на фронтенде). Задачи QA-01…QA-07
  из backlog не закрыты; при работе над доменом уведомлений, правами и worker
  тесты приёмочных сценариев пишутся вместе с кодом.
