# Соглашения API

Документ фиксирует общие правила, действующие для всех endpoint. Он принимается до
первого endpoint (задача INF-03 декомпозиции) и не может ослаблять доменные правила
технического задания.

Машиночитаемая спецификация: [swagger.yaml](swagger.yaml), [swagger.json](swagger.json).
Интерактивная документация поднимается вместе с API на `GET /docs/`.

## Базовый путь и версия

Все прикладные endpoint располагаются под `/api/v1`. Служебные пробы дополнительно
доступны по корневым псевдонимам `/healthz`, `/readyz` и `/metrics` — они не входят
в контракт API и предназначены инфраструктуре.

## Формат данных

* Тело запроса и ответа — `application/json; charset=utf-8`.
* Неизвестные поля в теле запроса отвергаются с кодом `400`.
* Все моменты времени передаются в UTC в формате RFC 3339: `2026-08-22T09:00:00Z`.
  Отображение — задача клиента, и идёт оно в личной таймзоне пользователя
  (`User.timezone`, раздел 4 ТЗ); системная зона (по умолчанию `Europe/Moscow`)
  остаётся запасным вариантом, когда личная не задана или нераспознаваема.
* Идентификаторы — UUID в каноническом строковом виде.
* Язык кода и ответов API — английский. `code` — стабильный английский
  идентификатор, `message` — английский запасной вариант для тех, кто читает
  API напрямую. Текст на экране клиент берёт из своего словаря по `code`
  (`frontend/src/shared/i18n/locales/<lang>/errors.json`); сервер язык клиента
  не угадывает. Продуктовые уведомления (письма, сообщения worker) приходят
  на языке получателя из словаря `backend/internal/locale/messages`.

## Схема ошибки

Любой ответ с кодом 4xx или 5xx имеет одинаковое тело:

```json
{
  "error": {
    "code": "validation_failed",
    "message": "invalid request data",
    "fields": [{ "field": "email", "message": "invalid email address" }],
    "request_id": "8f1c2b3a-..."
  }
}
```

`code` — стабильный машиночитаемый код, `message` — человекочитаемое пояснение,
`fields` присутствует только у ошибок валидации, `request_id` совпадает с заголовком
`X-Request-Id` и позволяет найти запрос в логах.

### Коды состояния

| Код | Когда возвращается |
|-----|--------------------|
| `200` | успешное чтение или изменение |
| `201` | создан новый объект |
| `202` | запрос принят, результат асинхронный (письмо отправлено) |
| `204` | успешное выполнение без тела |
| `400` | ошибка валидации входных данных |
| `401` | отсутствует или недействительна аутентификация |
| `403` | недостаточно прав, отсутствует или не совпадает CSRF-токен |
| `404` | объект не найден либо недоступен вызывающему |
| `409` | конфликт уникальности либо недопустимый переход состояния |
| `429` | превышено ограничение частоты запросов |
| `503` | сервис не готов (проверки `readyz` и heartbeat) |

### Политика 403 против 404

Если объект существует, но доступ к нему запрещён ролью, возвращается `403`.
Если объект не принадлежит вызывающему и сам факт его существования не должен
раскрываться (чужие назначения, чужие статусы), возвращается `404`.

## Аутентификация

Схема — cookie. `access_token` живёт 15 минут, `refresh_token` ротируется при каждом
обновлении и живёт 30 дней; оба выставляются как `HttpOnly; Secure; SameSite=Lax`.
Повторное использование отозванного refresh-токена отзывает всю цепочку сессии.

Все изменяющие запросы (`POST`, `PATCH`, `PUT`, `DELETE`) обязаны передавать CSRF-токен
заголовком `X-CSRF-Token`, значение которого совпадает с cookie `csrf_token`. Токен
выдаётся на `GET /api/v1/auth/csrf`; клиент запрашивает его перед первым изменяющим
запросом, включая вход.

## Пагинация

Списочные endpoint принимают `page` (с единицы) и `page_size` и возвращают конверт:

```json
{ "items": [], "meta": { "page": 1, "page_size": 50, "total": 137, "has_next": true } }
```

Значение `page_size` по умолчанию — 50, максимум ограничен конфигурацией. Поиск
пользователей для административных операций после 50 результатов продолжается только
через следующую страницу.

## Пакетные операции

Пакетные endpoint именуются суффиксом действия: `batch-add`, `batch-remove`,
`batch-set`, `copy-from`. Каждый элемент обрабатывается собственной транзакцией,
поэтому ответ содержит построчный результат:

```json
{
  "succeeded": 2,
  "skipped": 1,
  "failed": 0,
  "results": [
    { "index": 0, "status": "ok", "id": "..." },
    { "index": 1, "status": "skipped", "code": "already_assigned", "message": "the participant is already assigned" }
  ]
}
```

Пакетный запрос возвращает `200` даже при частичных отказах: конфликт отдельного
элемента не является ошибкой всей операции. Код 4xx отдаётся только тогда, когда
некорректен сам запрос или недоступен объект-контейнер.

Операции массовой установки статуса имеют парный endpoint `.../preview`, который
возвращает количество затрагиваемых и пропускаемых записей, ничего не изменяя.

## Идентификация запроса

Клиент может передать `X-Request-Id`; иначе сервер генерирует его сам. Значение
возвращается тем же заголовком, попадает в структурированные логи и в записи аудита.

## Что API не делает

* Не проверяет внешний сайт регистрации: статус регистрации — самоотчёт пользователя
  либо административно установленное состояние.
* Не изменяет флаг администратора — это операционная процедура вне пользовательского API.
* Не отдаёт `password_hash`, значения токенов и `telegram_chat_id`.
* Не поддерживает выгрузку аудита файлом и импорт/экспорт CSV — это решения после MVP.
