## Что осталось из фазы 1

`000058_retention_settings`, пакет `services/retention`, слой базы,

`make back-test-integration` после последней правки.

**Решение владельца по удалению событий.** Удалить событие с уведомлениями
нельзя: миграция `000004_notifications` держит `ON DELETE RESTRICT` и триггер
`notifications_no_delete`, который защищает дедупликацию по `logical_key`.
Это намеренное правило, а не дефект; у журнала аудита лазейка под
`app.audit_retention = 'on'` предусмотрена, у уведомлений — нет. Пока
удаление честно отвергается с внятным текстом. Три пути:

1. удалять только события без уведомлений — безопасно и почти бесполезно;
2. флаг `app.notification_retention` по образцу аудита — ценой того, что
   `logical_key` перестаёт быть вечной защитой от повтора;
3. не удалять события вовсе, только архивировать — данные целы, база растёт.

**B7 — письма другу.** Упирается в DNS домена `goatwhistle.ru`, не в код:
без SPF и DKIM письма через Gmail SMTP уходят в спам. Проверить может только
владелец домена. В фазе 2 к этому добавляется заголовок `List-Unsubscribe`

# Дорожка C — уведомления, письма, Telegram

## C1. Центр уведомлений на платформе

**Зачем.** Сейчас у человека есть колокольчик с типом и датой — и всё. Нельзя
прочитать, о чём уведомление, нельзя удалить, нельзя открыть список. Тело
существует, но уходит только на почту и в Telegram.

**Что сделать.**

Новая сущность «элемент входящих» (`inbox_items`): получатель, вид,
заголовок, тело в Markdown, ссылка на предмет (событие, команда, задача),
действия, `read_at`, `deleted_at`, `logical_key`. Отдельная таблица, а не
`notifications`: у тех запрещено удаление триггером, а входящие обязаны
удаляться. Одна деловая ситуация — одна запись: вставка `ON CONFLICT DO
NOTHING` по тому же `logical_key`, что и у доставки.

Наполнение: та же точка, где рождается уведомление для почты или Telegram,
рождает и элемент входящих. Плюс личные события из `system_events` для этого
пользователя. Тело и заголовок — из тех же словарей `notification.*`, что и
письма.

Контракт: `GET /me/inbox` с пагинацией и фильтром «непрочитанные»,
`GET /me/inbox/unread-count`, `POST /me/inbox/read` (список или всё),
`DELETE /me/inbox/{id}`, `DELETE /me/inbox` (всё или всё прочитанное),
`POST /me/inbox/{id}/restore` — удаление мягкое, с окном отмены. Счётчик
непрочитанных идёт через уже существующий канал реального времени
(`services/realtime`), не заводить второй.

Действия внутри элемента: «Открыть событие», «Я зарегистрировался» — та же
`MarkDone`, что у Telegram-кнопки, идемпотентная.

**Тонкости.**

* Удаление обязано быть мягким с окном отмены: тост «Удалено — вернуть» на
  несколько секунд, как принято в почтовых клиентах. Иначе «удалить всё» —
  необратимая кнопка на видном месте.
* Элемент входящих и уведомление в очереди живут разными жизнями: удаление
  из входящих не отменяет доставку, отмена доставки не удаляет входящие.
  Закрепить тестом, что дедупликация доставки не сломана.
* Старые записи чистить по удержанию из A5, а не копить вечно.

## C2. Письма, которые не стыдно показать

**Зачем.** Шаблон один, тёмная тема только по системной настройке
получателя, логотип старый, кнопка влево, а напоминания и дайджест вовсе
идут голым текстом. Владелец просил: тёмная тема по умолчанию, английский по
умолчанию, наш логотип, зависимость от темы и языка пользователя, красиво,
все виды.

**Что сделать.**

* **Все виды писем на один шаблон**: подтверждение адреса, восстановление,
  смена почты и её отмена, приглашение, смена пароля, первичное назначение,
  напоминание, просрочка, личная задача, ретроспектива, недельный дайджест.
  Напоминания и дайджест переезжают с чистого текста на HTML с текстовой
  альтернативой (multipart уже есть в `adapters/email`).
* **Тема из настроек пользователя.** Для этого тема должна храниться на
  сервере: поле `users.theme` (`dark | light | system`), контракт `PATCH
  /me` принимает его, панель «Внешний вид» сохраняет туда же, куда и в
  `localStorage` (это правка D, названа в D7). Правило рендера: `dark` и
  `system` → тёмная палитра **встроена в стили**, светлая — через
  `@media (prefers-color-scheme: light)`; `light` → наоборот. Нет
  пользователя (приглашение) → тёмная. Так тёмная получается по умолчанию,
  а не по случайности.
* **Язык из профиля**, без пользователя — английский. Умолчание везде —
  английский (C4).
* **Логотип — три полосы «Гант»**, тот же, что в `shared/ui/brand/logo-mark`.
  Gmail режет SVG и `data:`-картинки, поэтому логотип отдаётся файлом
  `frontend/public/brand/mark-dark.png` и `mark-light.png` по `PUBLIC_URL`, с
  текстовой подписью на случай отключённых картинок. Проверить отдельно:
  `img-src 'self'` в `nginx.conf` относится к SPA, письму не мешает.
* **Кнопка по центру**: у `.tl-btn` ячейка получает `align="center"` и
  таблица-обёртка с `margin: 0 auto` — иначе Outlook проигнорирует CSS.
* Прехедер под каждый вид, подвал «почему вы получили это письмо» со ссылкой
  на `/catalog?settings=notifications`, заголовок `List-Unsubscribe` — он
  же снижает вероятность спама.
* **Проверка на живой почте.** Команда CLI `timeline mail samples --to
  <адрес>` отправляет по одному письму каждого вида в обеих темах и обоих
  языках — 44 письма. Отправлять на `mikhailkhorokhorin@gmail.com`. Для этого
  локальный `.env` должен получить SMTP из `.env.server.local` (файл
  gitignored, не коммитить). Команда доступна только при `APP_ENV=dev`.

**Тонкости.**

* Письмо — это таблицы и инлайн-стили, не Tailwind. Токены палитры берутся
  из `styles/tokens/palette.css` **значениями**, а не переменными: в письме
  `var()` не работает. Чтобы hex в шаблоне не расходился с токенами, завести
  тест, сравнивающий цвета шаблона с `palette.css`.
* `template.html` — 117 строк, `mail` — небольшой пакет. Разрезать на
  каркас и блоки по видам через `//go:embed` каталога, иначе `file-length`
  остановит первый же новый вид.
* Тёмная тема в письме означает светлый текст на тёмном фоне у всех
  клиентов, включая те, что не понимают `color-scheme`. Поэтому цвета
  встроены, а `@media` — только для противоположной темы.

## C3. Telegram-сообщения того же уровня

**Что сделать.** `parse_mode: HTML`: жирный заголовок, строка дедлайна,
ссылка на событие, кнопки «Открыть» и «Я зарегистрировался». Структура
повторяет письмо: заголовок → суть → срок → действие. После нажатия
«Я зарегистрировался» сообщение **редактируется** (`editMessageText`),
показывая отметку, а не остаётся с живой кнопкой. Экранирование HTML для
названий событий обязательно — иначе `<` в имени сломает сообщение.

## C4. Английский по умолчанию

**Что сделать.** `DEFAULT_LOCALE = 'en'` на фронтенде, `locale.Default =
"en"` на сервере, новый пользователь без явного выбора — `en`. Порядок
определения на фронтенде остаётся: профиль → сохранённый выбор → язык
браузера → умолчание.

**Тонкость.** Тест языка в `telegramlink/reply_test.go` нарочно использует
`en-GB`, потому что умолчание `ru` маскировало ошибку. После смены умолчания
такие тесты обязаны использовать `ru`, иначе снова замаскируют. Пройти по
всем тестам, где умолчание участвует в ожидании.

## C5. Публичный профиль — данные для настоящей страницы

**Зачем.** Сейчас `GET /profiles/{nickname}` отдаёт имя, ник, аватар,
описание и список событий из названия и дат. Для страницы уровня GitHub
этого мало: нет ролей, результатов, команд, ссылок, даты появления и
никакой статистики. Страницу строит D (D9), данные даёт эта задача.

**Что сделать.**

* **Ссылки профиля**: новая таблица `profile_links` (пользователь, тип,
  URL, порядок) — сайт, GitHub, Telegram, LinkedIn, произвольная. Тип
  определяется по адресу через уже существующий `detectService` из
  `shared/ui/navigation/service-link`, глиф берётся оттуда же. `PATCH /me`
  принимает список, публичный профиль его отдаёт. Не больше восьми.
* **События с ролью и исходом**: к каждому событию в ответе — вид
  (хакатон или митап), роль (участник, организатор), команда, если участие
  командное, и исход, если он известен: место и приз из данных финансов.
  Ничего не выдумывать: если исход не записан, поля нет.
* **Сводка**: число событий, число команд, «с нами с» из `created_at`,
  доля регистраций, отмеченных до дедлайна — из `registration_statuses`.
  Последнее показывать только владельцу профиля и администратору: это
  оценка дисциплины, а не публичная витрина.
* **Активность по месяцам** за последний год для тепловой полосы: сколько
  событий шло в каждом месяце. Один запрос агрегатом, без N+1.
* **Видимость**: поле `profile_visibility` (`public | members | private`).
  `members` — только вошедшим, `private` — только себе; чужой закрытый
  профиль отвечает `404`, а не `403`: по политике проекта сам факт
  существования раскрывать нельзя.
* **Закреплённые события**: до трёх, выбирает владелец; хранить в профиле
  списком идентификаторов.

**Тонкости.**

* Показывать можно только опубликованные события: неопубликованное через
  чужой профиль утекать не должно, это закрепить тестом.
* Команды тоже могут быть закрытыми — уважать их видимость, а не
  профиля.
* Наружу уходят `display_id`, никаких UUID — тест `no-uuid-in-responses`
  это поймает, но лучше не доводить.

# Дорожка D — оболочка

## D1. Палитра Ctrl+K — вторая версия

**Зачем.** Сейчас палитра ищет только команды и заканчивается кнопкой с
текстом «Перейти». Владелец хочет поиск по сущностям с префиксами, свои
разделы, админский режим и подсказку по знакам.

**Что сделать.**

* Кнопка «Перейти» становится иконкой стрелки с подписью для чтения с
  экрана; в строке результата справа — `kbd` с подсказкой `↵`.
* **Префиксы**: `#` — хакатоны по названию, `@` — митапы, `*` — и то и
  другое, `>` — команды, `/` — страницы, `~` — команды участников, `!` —
  админские действия (видны и работают только у администратора, у остальных
  префикс не подсказывается и не срабатывает). Без префикса — умный поиск
  по всему сразу, сгруппированный по разделам.
* **Подсказка** — знак `?` в углу поля, по нажатию раскрывает список
  префиксов с примерами; тот же список открывается, если ввести только `?`.
* Недавние переходы — до пяти, в `localStorage`.
* Поиск сущностей — через API, а не по кэшу: `GET /events?q=` (проверить,
  что каталог его уже принимает) и аналог для команд. Дебаунс, отмена
  устаревших запросов, состояние «ищем».

**Тонкости.**

* Это комбобокс: `role="combobox"`, `aria-activedescendant`, стрелки,
  `Home/End`, `Esc` закрывает, `Tab` не уходит в никуда.
* `matchesQuery` из `shared/keyboard/layout-map` уже умеет искать при
  неправильной раскладке — сохранить это для сущностей, не только для
  команд.
* Дизайн — через `impeccable` и `ui-ux-pro-max`; палитры скилла не брать,
  токены наши (правило `CLAUDE.md`).

## D2. Календарь «прилетает слева»

**Причина по коду.** `date-picker.tsx` не использует общий `Popover`: у него
собственный `use-anchored-panel.ts`, панель монтируется в `top: 0, left: 0`
с `visibility: hidden`, а координаты и класс анимации приходят одновременно
следующим кадром. Это вторая реализация всплывающей поверхности при том, что
правило «одна всплывающая поверхность» в проекте уже закреплено.

**Что сделать.** Перевести календарь на `@radix-ui/react-popover` с
`FLOATING_MOTION` из `overlay-chrome.ts` — тогда анимация станет той же, что
у всех попапов. Удалить `use-anchored-panel.ts`. Закрепить ratchet-тестом:
ни один компонент вне `overlays/` не вычисляет `top/left` для `fixed`-панели.

**Тонкость.** Проверить именно в аудите и в трёх остальных местах, где
`DatePicker` используется, — тесты движение не видят. Если после переезда
эффект останется, причина в другом, и её надо найти в браузере, а не
закрывать задачу.

## D3. Один глиф Telegram

**Что сделать.** `TelegramMark` несёт фирменный цвет **сам**, по умолчанию;
внешний `className` не обязан его добавлять. Оба вызова становятся
одинаковыми. Тест: `TelegramMark` не рендерится без цвета.

## D4. Язык на входе и регистрации

**Что сделать.** Справа сверху — иконка глобуса, по нажатию — выбор языка с
`LanguageFlag` из `features/appearance/`, тот же вид, что во «Внешнем
виде». Выбор пишется в `localStorage` под `timeline-locale` и после входа
переносится в профиль. Умолчание — английский (C4).

**Тонкость.** Страницы входа не под `AppShell`, поэтому это отдельная
маленькая шапка в `AuthLayout`, а не переиспользование сайдбара. Меню — на
общем `Popover`.

## D5. Ввод денег с разрядами

**Что сделать.** Компонент `MoneyInput`: группировка разрядов по локали
(`ru` — тонкий пробел, `en` — запятая) прямо при вводе, `inputMode=
"numeric"`, вставка из буфера с любыми разделителями, каретка не прыгает.
Хранится целое число, как и сейчас. Применить к призам трека, призу кейса и
фонду события.

**Тонкость.** Сохранение каретки при форматировании — единственная
сложность, и её надо покрыть тестом: ввод в середине числа, удаление
разделителя, вставка.

## D6. Переход между входом и регистрацией

**Что сделать.** Обе страницы уже под `AuthLayout`. Внутри — перекрёстное
затухание с лёгким сдвигом: вход → регистрация уезжает влево, обратно —
вправо. Высота контейнера не прыгает: анимировать через `grid-template-rows`
или фиксировать минимальную высоту. Фокус после смены — на первое поле.
`motion-safe:` обязателен: это движение, а не смена цвета.

## D7. Тема в профиле

Малая правка ради C2: панель «Внешний вид» сохраняет тему ещё и в профиль
через `PATCH /me`, контракт пишет C. Без этого письмо не узнает тему.

## D8. Центр уведомлений — экран

По контракту из C1. Колокольчик показывает последние пять с заголовком и
началом тела, снизу «Все уведомления». Страница `/inbox`: список с
группировкой по дням, фильтр «непрочитанные», выбор нескольких, «прочитать
всё», «удалить всё», «удалить прочитанные», тост с отменой, пустое
состояние. Клавиатура: `j/k` по списку, `x` выбор, `Esc` сброс. Разметка
элемента — тот же визуальный язык, что и у письма из C2: заголовок → суть →
срок → действие.

## D9. Публичная страница человека — как на GitHub

**Зачем.** Владелец открыл свою страницу `/@nickname` и увидел дверь в
продукт: логотип, слоган, полоски этапов и две карточки сбоку. Причина по
коду: маршрут `/:handle` смонтирован под `AuthLayout` — тем же каркасом,
что вход и регистрация. Страница человека не должна выглядеть как экран
входа.

**Что сделать.**

* **Свой каркас.** Вошедший видит страницу внутри `AppShell`, с сайдбаром и
  колокольчиком, как любой раздел. Гость видит её под лёгкой публичной
  шапкой: логотип, глобус языка (D4), кнопка «Войти». `AuthLayout` для
  неё больше не используется.
* **Шапка профиля в две колонки**, как на GitHub. Слева, узкая колонка:
  крупный аватар, имя, `@ник`, описание в Markdown, ряд ссылок с глифами
  сервисов, «с нами с» и кнопка «Редактировать профиль» у владельца,
  «Поделиться» — копирует ссылку. Справа, широкая: содержимое.
* **Содержимое, сверху вниз:**
  1. Закреплённые события — до трёх карточек в ряд с видом, датами,
     ролью и исходом; у владельца в углу каждой — «открепить».
  2. Тепловая полоса активности за год по месяцам, как график
     контрибуций: пустой месяц тусклый, насыщенность растёт с числом
     событий. Наведение показывает месяц и счёт. Цвета — токены, четыре
     ступени, различимы и в светлой, и в тёмной теме; проверить контраст
     глазами.
  3. Хронология участия по годам: год — заголовок, под ним события
     списком, новые сверху. У каждого — вид, даты, команда, исход.
     Победы и призовые места помечены медалью из `PrizeMark`; это тот же
     визуальный язык, что на странице финансов.
  4. Команды, в которых человек состоит, — если команда открыта.
* **Сводка** в узкой колонке под ссылками: события, команды, победы.
  Доля вовремя отмеченных регистраций — только владельцу и
  администратору, как решено в C5.
* **Пустые состояния** честные: «Пока ни одного события» у новичка вместо
  пустой хронологии; у самого владельца — с подсказкой, куда идти.
* **Своя страница и чужая различаются** ровно тремя вещами: кнопка
  редактирования, закрепление и приватная сводка. Всё остальное владелец
  видит таким же, каким его видят другие, — иначе он не узнает, как
  выглядит снаружи.
* **Заголовок вкладки и метатеги**: имя и ник в `<title>`, описание и
  аватар в `og:*` — ссылку на профиль будут кидать в чаты.

**Тонкости.**

* Закрытый или несуществующий профиль — один и тот же экран «нет такой
  страницы», без различия: политика `404` из `CLAUDE.md`.
* Ширина: на телефоне колонки складываются, шапка идёт первой, полоса
  активности прокручивается горизонтально внутри своего контейнера, не
  ломая страницу.
* `MarkdownView` для описания уже настроен строго: без картинок, ссылки с
  `rel="noopener noreferrer"`. Не ослаблять.
* Тепловая полоса — это график: сначала прочитать `dataviz`, потом
  рисовать. Легенда обязательна, без неё четыре оттенка ничего не значат.
* Дизайн — через `impeccable` и `ui-ux-pro-max`, палитры скилла не брать.

# Порядок и распределение

## Дорожка C (агент 1)

1. **C4 английский по умолчанию** — маленькая, но задевает тесты; первой
2. **C1 центр уведомлений: контракт** — swag → `make back-docs` →
   `make types`, чтобы D мог начинать D8
3. **C5 публичный профиль: контракт** — ссылки, роли, исходы, видимость,
   чтобы D мог начинать D9
4. **C2 письма** — самая крупная, включает поле темы в профиле
5. **C1 реализация** — сервис, наполнение, реальное время
6. **C5 реализация** — таблица ссылок, агрегаты, видимость
7. **C3 Telegram**

## Дорожка D (агент 2)

1. **D3 глиф Telegram** — минуты
2. **D2 календарь** — заметный дефект
3. **D5 ввод денег**
4. **D4 язык на входе**
5. **D6 переход вход/регистрация**
6. **D7 тема в профиле** — когда C выпустит контракт
7. **D9 публичная страница** — когда C выпустит контракт C5; сначала
   вынести маршрут из `AuthLayout`, это можно и до контракта
8. **D1 палитра** — крупная
9. **D8 центр уведомлений** — когда C выпустит контракт C1

## Общие правила для обеих дорожек

* Контракт первым: аннотации swag → `make back-docs` → `make types`.
* Миграции только вперёд, парой `.up/.down`; следующий номер — `000059`.
* Каждое правило — тест, каждый тест — проверен мутацией: сломать,
  убедиться, что падает **названный** тест, восстановить байт в байт и
  сверить контрольную сумму.
* Тесты не видят экран: анимации, выравнивание, письма в почтовом клиенте
  — только глазами. Письма — только на живой ящик.
* Интеграционные тесты Go — только `make back-test-integration`.
* Русский — только в `docs/` и словарях локализации.
* Git-операции агентам запрещены; коммитит координатор, пушит владелец.
* `impeccable` и `ui-ux-pro-max` — на всей визуальной работе D и на
  шаблонах писем C; при расхождении со `CLAUDE.md` побеждает `CLAUDE.md`.
