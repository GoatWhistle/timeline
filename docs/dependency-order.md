# Порядок реализации MVP по зависимостям

Документ построен по полям `Зависит` из `tasks.md`. Он не меняет состав MVP, а исправляет порядок выполнения: задача из следующей волны начинается только после завершения всех её зависимостей из предыдущих волн. Задачи внутри одной волны можно выполнять параллельно.

## 2. Рекомендуемый порядок поставки

Для разработки одним человеком с агентом лучше закрывать не технические слои целиком, а рабочие вертикальные срезы. Внутри каждого этапа стрелка означает обязательную последовательность; элементы через `+` можно вести параллельно.

### Этап 0 — зафиксировать спорные решения

До генерации кода нужно принять и записать решения для `INF-03`:

- схема ошибок, пагинации, batch-result и политика `403`/`404`;
- схема refresh-token family и обнаружение повторного использования старого токена;
- способ обеспечить межтабличное правило `registration.deadline_at <= hackathon.end_at`;
- способ обеспечить максимум 10 правил на Registration — обычный PostgreSQL `CHECK` не умеет считать соседние строки;
- формат CSRF, требования к паролю и нормализация email;
- dev-адаптеры Email/Telegram и выбранные production-провайдеры;
- целевая схема deployment, домены и секреты окружения.

### Этап 1 — воспроизводимый фундамент

`INF-01 + INF-03` → `BE-01 + FE-01` → `BE-02 + BE-03 + BE-04 + BE-05 + BE-27 + FE-02` → `INF-02 + QA-02`.

Результат: проект поднимается одной командой, миграции применяются с чистого состояния, OpenAPI генерирует frontend-типы, ограничения БД проверяются интеграционными тестами.

`BE-27` намеренно перенесён сюда: от него зависят деактивация пользователя, Registration, Participants и весь notification pipeline.

### Этап 2 — идентификация и доступ

`BE-06 + BE-08 + BE-31 + BE-32 + BE-36` → `BE-07 + BE-09 + BE-10 + BE-14 + BE-17` → `BE-11 + BE-12 + BE-13 + BE-15 + BE-16 + BE-37`.

Параллельно frontend: `FE-03` → `FE-04` → `FE-05 + FE-08` → `FE-06 + FE-07 + FE-09 + FE-10`.

Завершение этапа: `QA-03` и интеграционный сценарий register → verify → login → refresh → logout.

### Этап 3 — главный продуктовый поток

Backend:

`BE-18` → `BE-19` → `BE-21 + BE-24` → `BE-22 + BE-25 + BE-26` → `BE-23`.

Frontend администратора:

`FE-15` → `FE-16` → `FE-17 + FE-18 + FE-21` → `FE-19 + FE-20 + FE-23`.

Frontend пользователя:

`FE-11` → `FE-12`.

Результат: администратор создаёт и публикует хакатон, настраивает регистрацию, назначает участника; пользователь видит назначение и переводит свой статус из TODO в DONE. На этом этапе внешняя доставка может использовать fake/dev providers, но строки Notification и их `logical_key` должны создаваться по настоящим правилам.

### Этап 4 — доставка уведомлений

`BE-28 + BE-30` → `BE-29` → `BE-34 + QA-04`; параллельно выполняются `BE-20`, `BE-35`, `QA-01` и `INF-06` после появления их зависимостей.

Результат: scheduler, дедупликация, версии, отмена, retry, fallback каналов, lease recovery и метрики проверены автоматическими тестами. После тестовых адаптеров подключаются реальные Telegram и Email credentials.

### Этап 5 — read-модели и Timeline

`BE-25` → `BE-33`; frontend: `FE-13` → `FE-14 + FE-22`; затем `FE-24`.

Результат: пользовательские и административные списки и Timeline работают с реальным API, фильтры сохраняются в URL, критические экраны проходят keyboard/a11y-проверку.

### Этап 6 — выпуск

`INF-04` → `INF-05` → `QA-07`; после готовности `BE-33` и тестового deployment выполняется `QA-06`. Последней запускается `QA-05`, причём практически она требует не только `FE-24`, но и готовых backend API, PostgreSQL и provider stubs.

Результат: staging/production deployment, миграции, backup/restore, наблюдаемость, performance и полный сценарий «создать → опубликовать → назначить → отметить регистрацию → остановить напоминания».

## 3. Что исправлено по сравнению с исходным порядком

- `BE-16` раньше находилась перед своей зависимостью `BE-27`; теперь `BE-27` выполняется в фундаменте.
- `BE-20` раньше находилась перед своей зависимостью `BE-28`; теперь изменение дат выполняется после появления reconciliation.
- `BE-22` и `BE-24` раньше находились перед своей зависимостью `BE-27`; теперь модель Notification создаётся до предметного потока.
- `QA-06` раньше находилась в одном этапе с `INF-04`; теперь performance-проверка запускается после готового тестового deployment.
- Зависимости frontend от работающих endpoint не входят в топологические волны разработки на моках; отдельная таблица интеграционной приёмки зафиксирована в [tasks.md](tasks.md).

## 4. Критические цепочки

Основной продуктовый поток:

`INF-01` → `BE-01` → `BE-02 + BE-03` → `BE-04` → `BE-18` → `BE-19 + BE-27` → `BE-24` → `BE-22 + BE-25` → `BE-33`.

Уведомления:

`BE-04` → `BE-27` → `BE-28 + BE-30` → `BE-29` → `BE-34` → `INF-06`.

Frontend и e2e:

`INF-01 + INF-03` → `FE-01` → `FE-02` → `FE-03` → `FE-04` → ветки пользовательских и административных экранов → `FE-24` → `QA-05`.

## 5. Правило работы с агентом

Каждая задача считается готовой только вместе с миграцией или OpenAPI-изменением, тестами её приёмочных сценариев и проверкой всех уже завершённых сценариев. Следующую задачу нельзя начинать только потому, что предыдущая сгенерировала код: сначала должны проходить сборка, линтеры и релевантные тесты.
