# Задачи MVP

**Hackathon Tracker** · декомпозиция технического задания v0.8

Список закрывает разделы 1–18 ТЗ и приёмочные сценарии раздела 19. Матрица покрытия — в конце документа.

## Как читать

| Обозначение | Значение |
|----|----|
| INF | Инфраструктура и общие соглашения; делается совместно |
| BE | Backend, Go |

# Инфраструктура и соглашения

## INF-01. Репозиторий и локальная разработка

Структура монорепозитория: `backend/`, `frontend/`, `deploy/`, `docs/`. Docker Compose поднимает PostgreSQL, backend, worker и frontend одной командой. Файл `.env.example` содержит все параметры приложения C ТЗ.

- ТЗ: 14, 14.1
- Блокирует: BE-01, FE-01

## INF-02. CI на GitHub Actions

Пайплайн на каждый pull request: сборка backend и frontend, линтеры, unit-тесты, интеграционные тесты на поднятой PostgreSQL. Публикация Docker-образов на merge в основную ветку.

- ТЗ: 14.1, 18
- Зависит: INF-01

## INF-03. Соглашения API и скелет OpenAPI

Фиксируются до первого endpoint: единая схема ошибки, формат пагинации, формат результата batch-операции с per-item статусом, правила именования путей, коды ответов для конфликтов и запретов. Скелет OpenAPI с общими компонентами.

- ТЗ: 17
- Блокирует: BE-09, FE-02

## INF-04. Развёртывание

Docker-образы backend, worker и frontend на одном сервере за reverse proxy с TLS. Прогон миграций при деплое. Runbook отката.

- ТЗ: 14, 14.1, 18
- Зависит: INF-02

## INF-05. Резервное копирование PostgreSQL

Ежедневный шифрованный backup, хранение 7 дней. Документированная и проверенная процедура восстановления.

- ТЗ: 18, 22
- Зависит: INF-04

## INF-06. Наблюдаемость

Структурированные JSON-логи с `request_id` и запретом на секреты, токены и полный payload уведомлений. Экспорт метрик Prometheus. Базовые дашборды: возраст очереди, FAILED и UNDELIVERABLE, ошибки провайдеров, зависшие PROCESSING.

- ТЗ: 13, 18
- Зависит: BE-34

# Backend

## BE-01. Каркас приложения

Точки входа API и worker в одной кодовой базе. Загрузка конфигурации из окружения по приложению C ТЗ. Структура пакетов по модулям раздела 14: identity, event, participation, registration, notification, query, audit. Корректное завершение по сигналу.

- ТЗ: 14, 14.1
- Зависит: INF-01
- Блокирует: все остальные BE

## BE-02. Миграции: идентификация

Таблицы `users`, `sessions`, `one_time_tokens`, `invites`. Уникальность нормализованного email, `pending_email`, `telegram_chat_id`, `refresh_token_hash`, `token_hash`. Частичная уникальность одного непринятого и неотозванного приглашения на email.

- ТЗ: 3, 4, 15
- Зависит: BE-01

## BE-03. Миграции: события и этапы

Таблицы `events`, `stages`. Проверки `end_at > start_at`, HTTPS для URL, значения enum типа этапа.

- ТЗ: 5, 15
- Зависит: BE-01

## BE-04. Миграции: участие, регистрация, уведомления, аудит

Таблицы `event_participants`, `registrations`, `registration_statuses`, `notification_rules`, `notifications`, `audit_log`.

Обязательные ограничения на уровне базы:

- `UNIQUE(event_id, user_id)` для участников;
- `UNIQUE(event_id)` для регистрации;
- `UNIQUE(registration_id, participant_id)` для статусов;
- составное ограничение общего `event_id` у статуса, регистрации и участника — составными внешними ключами либо constraint trigger;
- ограничение `deadline_at <= events.end_at` через `UNIQUE(events.id, end_at)`, денормализованную копию `event_end_at` в регистрации, составной внешний ключ с `ON UPDATE CASCADE` и локальный `CHECK`; обычный `CHECK` чужую таблицу не видит;
- `UNIQUE(registration_id, offset_minutes)` и `CHECK` диапазона `-525600..525600`;
- ограничение числа правил десятью через `slot_no` с `CHECK slot_no BETWEEN 1 AND 10` и `UNIQUE(registration_id, slot_no)`; обычный `CHECK` соседние строки не считает;
- `UNIQUE(logical_key)` для уведомлений;
- `CHECK` неотрицательных версий и счётчиков;
- запрет прямых UPDATE и DELETE по `audit_log` для runtime-роли базы.

- ТЗ: 6, 7, 8, 9, 13, 15
- Зависит: BE-02, BE-03
- Приёмка: AC-REG-05

## BE-05. Хеширование паролей

Argon2id с параметрами из конфигурации. Пароль и хеш не попадают в ответы API, логи и снимки аудита.

- ТЗ: 3, 4
- Зависит: BE-01

## BE-06. Сессии и токены

Access token в виде JWT в HttpOnly Secure SameSite=Lax cookie, срок 15 минут. Refresh token — непрозрачное случайное значение, в базе только хеш, срок 30 дней, ротация при каждом обновлении. Повторное использование отозванного refresh отзывает всю цепочку сессии.

- ТЗ: 3, 14.1
- Зависит: BE-02, BE-05

## BE-07. CSRF и CORS

Обязательный CSRF-токен для всех изменяющих запросов с cookie-аутентификацией. CORS разрешает только сконфигурированные origins.

- ТЗ: 3, 18
- Зависит: BE-06

## BE-08. Ограничение частоты запросов

Login: 10 попыток за 15 минут на пару IP и email. Сброс пароля и повторная отправка приглашения: 5 в час на пару IP и email. Значения конфигурируемы.

- ТЗ: 3
- Зависит: BE-01

## BE-09. Регистрация и подтверждение email

Регистрация, выдача одноразового токена подтверждения на 24 часа, подтверждение, повторная отправка. До подтверждения вход разрешён, продуктовые письма запрещены. Письма verification, reset и invite отправляются независимо от подтверждения.

- ТЗ: 3
- Зависит: BE-06, BE-08, INF-03, BE-32
- Приёмка: AC-AUTH-01

## BE-10. Вход, выход, обновление сессии

Login, logout, logout всех сессий, обновление пары токенов.

- ТЗ: 3
- Зависит: BE-06

## BE-11. Восстановление пароля

Одноразовый токен на 30 минут. После смены пароля все активные сессии пользователя отзываются.

- ТЗ: 3
- Зависит: BE-09
- Приёмка: AC-AUTH-03

## BE-12. Смена email

Новый адрес хранится как `pending_email` и становится основным только после подтверждения. До подтверждения вход работает по прежнему адресу. Уникальность проверяется для обоих полей.

- ТЗ: 3, 4
- Зависит: BE-09
- Приёмка: AC-AUTH-04

## BE-13. Приглашения

Создание, отзыв и список для администратора; публичный просмотр и принятие. Создание и повторная отправка сериализуются по нормализованному email: предыдущее приглашение отзывается, затем создаётся новое. После успешной регистрации остальные неистёкшие приглашения этого адреса отзываются в той же транзакции. Приглашение на адрес существующего пользователя отклоняется конфликтом независимо от его активности.

- ТЗ: 3
- Зависит: BE-09
- Приёмка: AC-AUTH-02, AC-AUTH-05, AC-AUTH-06

## BE-14. Профиль

Чтение и изменение своего профиля, выбор предпочитаемого канала. `is_admin`, `telegram_chat_id` и `password_hash` недоступны для изменения через этот endpoint.

- ТЗ: 4
- Зависит: BE-06

## BE-15. Привязка Telegram

Одноразовый deep-link или токен, связанный с текущим пользователем. `chat_id` устанавливается только этим потоком. Отвязка удаляет `chat_id`.

- ТЗ: 3, 4
- Зависит: BE-14, BE-31

## BE-16. Деактивация и удаление аккаунта

Деактивация обратима: `is_active` в false, отзыв сессий, удаление привязки Telegram, перевод всех PENDING-уведомлений получателя в CANCELLED. Обратная активация доступна администратору и не воскрешает отменённые уведомления. Удаление необратимо: удаление учётных данных и каналов, обезличивание имени и email, сохранение ссылок участия и аудита.

- ТЗ: 2, 3, 4, 16
- Зависит: BE-27
- Приёмка: AC-NOTIF-18

## BE-17. Авторизация и запрет межпользовательского доступа

Middleware проверки роли и владения ресурсом на каждом endpoint. Обычный пользователь не читает административные заметки и не изменяет чужие объекты. Отказы фиксируются как события безопасности.

- ТЗ: 2, 18
- Зависит: BE-06
- Приёмка: AC-AUTHZ-01

## BE-18. Аудит

Общий механизм записи: актор, действие, тип и идентификатор объекта, изменённые бизнес-поля до и после, `request_id`. Учётные данные и токены исключаются. Административное чтение с фильтрами и пагинацией; выгрузка файлом не поддерживается.

- ТЗ: 13, 17
- Зависит: BE-04
- Приёмка: AC-AUDIT-01

## BE-19. События

Создание, изменение, чтение, публикация, архивирование. Вычисляемое состояние UPCOMING, ACTIVE, FINISHED с приоритетом ARCHIVED. Административные заметки доступны только администратору. Публикация запускает согласование уведомлений и создаёт отложенные первичные уведомления.

- ТЗ: 5.1, 16
- Зависит: BE-03, BE-18
- Приёмка: AC-HACK-01

## BE-20. Изменение дат события

Изменение `start_at` и `end_at` с аудитом. Изменение `end_at` увеличивает `schedule_version` регистрации, отменяет устаревшие PENDING и запускает согласование. Нарушение ограничения `deadline_at <= end_at` отклоняется.

- ТЗ: 5.1, 14, 16
- Зависит: BE-19, BE-28
- Приёмка: AC-HACK-02

## BE-21. Этапы

Создание, изменение, удаление, список по событию. Пересечения этапов и выход за период события допускаются. Этап не порождает уведомлений.

- ТЗ: 5.2
- Зависит: BE-19

## BE-22. Участники

Массовое добавление, изменение роли, массовое удаление, реактивация. Повторное добавление реактивирует существующую запись, увеличивает `assignment_version`, очищает `removed_at` и заново задаёт роль. Удаление переводит в REMOVED и отменяет PENDING. Назначение, статус, первичное уведомление и аудит выполняются одной транзакцией; первичное уведомление включается в неё только для опубликованного неархивного события. Batch возвращает результат по каждому элементу.

- ТЗ: 6, 12, 14, 16
- Зависит: BE-24, BE-27
- Приёмка: AC-PART-01, AC-PART-02, AC-PART-03, AC-PART-04, AC-BATCH-01

## BE-23. Копирование состава

Перенос только ASSIGNED участников из другого события. Роль переносится как значение по умолчанию и может быть изменена до сохранения. Конфликты существующих участников пропускаются и возвращаются в результате.

- ТЗ: 12
- Зависит: BE-22

## BE-24. Регистрация

Создание, изменение, чтение, включение и выключение. Ведение `schedule_version`, `activation_version` и `notification_content_version`. Создание активной регистрации создаёт недостающие статусы TODO; первичные уведомления создаются только для опубликованного неархивного события. Выключение отменяет PENDING. Включение увеличивает версии активации и расписания. Изменение ссылки увеличивает версию контента, отменяет PENDING и запускает согласование. Жёсткое удаление после появления статусов запрещено.

- ТЗ: 7, 14, 16
- Зависит: BE-19, BE-27
- Приёмка: AC-REG-01, AC-REG-04, AC-REG-06, AC-NOTIF-11

## BE-25. Статусы регистрации

Пользовательский переход TODO в DONE для своей записи при активной регистрации, назначенном участии и неархивном событии. Административные переходы TODO в DONE, DONE в TODO, TODO и DONE в NOT_REQUIRED, NOT_REQUIRED в TODO. Вход в TODO увеличивает `todo_cycle` и очищает `registered_at`. Каждый переход отменяет будущие PENDING и пишется в аудит. Массовая установка TODO и NOT_REQUIRED с предварительным подсчётом изменений.

- ТЗ: 8, 12, 16
- Зависит: BE-24
- Приёмка: AC-REG-02, AC-REG-03

## BE-26. Правила уведомлений

Список, создание, изменение, выключение для регистрации. Знаковый `offset_minutes`: положительный даёт напоминание до дедлайна, отрицательный — уведомление о просрочке. Не более 10 правил на регистрацию, ограничение выражено через `slot_no`. Изменение полей расписания увеличивает `schedule_version` один раз на транзакцию и запускает согласование.

- ТЗ: 9.1, 9.5
- Зависит: BE-24
- Приёмка: AC-NOTIF-09

## BE-27. Модель уведомления

Таблица уведомлений как очередь. Сборка `logical_key` по трём форматам: первичное, напоминание, просрочка. Неизменяемый снимок payload с названием события, ссылкой, дедлайном в UTC и системной таймзоне. Русские шаблоны трёх типов. Изменение названия события не меняет существующий payload.

- ТЗ: 9.2, 9.3, 9.6
- Зависит: BE-04
- Приёмка: AC-NOTIF-12

## BE-28. Планировщик и согласование

Запуск не реже одного раза в 5 минут. Обработка только опубликованных неархивных событий, активных регистраций, назначенных участников, статусов TODO и активных пользователей. Создание отложенных первичных уведомлений, напоминаний и уведомлений о просрочке. Правило считается наступившим при `now >= deadline_at - offset_minutes`. Правило с неотрицательным смещением не срабатывает после дедлайна; правило с отрицательным не создаётся после `end_at` события. Конкурентные экземпляры вставляют запись с уникальным `logical_key`, конфликт считается успешной идемпотентной обработкой.

- ТЗ: 9.4, 9.5
- Зависит: BE-27
- Приёмка: AC-NOTIF-01, AC-NOTIF-02, AC-NOTIF-03, AC-NOTIF-10, AC-NOTIF-15

## BE-29. Worker доставки

Выборка готовых записей с блокировкой и пропуском занятых, перевод в PROCESSING, аренда на 2 минуты. Перед вызовом провайдера повторная проверка статуса, версий, участника, регистрации, события и активности получателя; неактуальная запись отменяется. Атомарная фиксация момента начала вызова, после которого гарантированная отмена невозможна. Повторы через 1, 5 и 30 минут, не более четырёх вызовов всего, затем FAILED. Возврат просроченной аренды в PENDING восстановительной задачей. Передача идентификатора уведомления как ключа идемпотентности провайдеру.

- ТЗ: 9.4, 9.5
- Зависит: BE-28, BE-30
- Приёмка: AC-NOTIF-06, AC-NOTIF-07, AC-NOTIF-08, AC-NOTIF-14

## BE-30. Выбор канала

Порядок: переопределение канала в правиле, предпочитаемый канал пользователя, запасной порядок Telegram затем Email. Недоступный канал отсеивается до вызова и попытку не тратит. Постоянная ошибка провайдера закрывает канал, worker в том же проходе переключается на следующий без задержки, счётчик попыток увеличивается. Отсутствие доступных каналов или закрытие всех даёт терминальный статус UNDELIVERABLE без изменения статуса регистрации.

- ТЗ: 10
- Зависит: BE-27
- Приёмка: AC-NOTIF-04, AC-NOTIF-05, AC-NOTIF-13, AC-NOTIF-16, AC-NOTIF-17

## BE-31. Адаптер Telegram

Отправка сообщения по `chat_id`, разбор постоянных и временных ошибок, обработка deep-link привязки. Учётные данные — секреты развёртывания.

- ТЗ: 10, 14
- Зависит: BE-01

## BE-32. Адаптер Email

Отправка писем аутентификации и продуктовых уведомлений, разбор постоянных и временных ошибок, различение неверного адреса и временного отказа.

- ТЗ: 3, 10, 14
- Зависит: BE-01

## BE-33. Модели чтения

Мои события с фильтром архивных, детальная карточка назначенного события, пользовательская и административная временная шкала с фильтрами по состоянию, участнику и диапазону, выборки ближайших и просроченных.

- ТЗ: 11, 17
- Зависит: BE-25
- Приёмка: AC-UI-01

## BE-34. Служебные endpoint

Проверка живости и готовности API, heartbeat worker, защищённый endpoint метрик Prometheus.

- ТЗ: 17, 18
- Зависит: BE-29

## BE-35. Очистка по срокам хранения

Через 90 дней очищается только `payload_json` уведомления; строка и `logical_key` сохраняются. Удаление строк уведомлений запрещено. Аудит хранится 365 дней и очищается отдельной операционной процедурой.

- ТЗ: 4, 13
- Зависит: BE-27
- Приёмка: AC-NOTIF-19

## BE-36. Первый администратор

Создание первого администратора через seed или конфигурацию при развёртывании. Флаг администратора не изменяется пользовательским API; изменение выполняется операционной процедурой и пишется в аудит.

- ТЗ: 2
- Зависит: BE-02

## BE-37. Поиск пользователей для административных операций

Административный endpoint поиска зарегистрированных пользователей по `display_name` и нормализованному `email`. Результат содержит только минимальные данные, необходимые для выбора участника: `id`, `display_name`, `email` и `is_active`; credentials и данные каналов не возвращаются. Поиск поддерживает пагинацию, а при количестве результатов больше 50 продолжение доступно только через следующую страницу. Endpoint доступен только администратору; добавление в событие неактивного пользователя отклоняется предметной операцией BE-22.

- ТЗ: 2, 12, 17
- Зависит: BE-14, BE-17

# Frontend

## FE-01. Каркас приложения

Vite, TypeScript в строгом режиме, Tailwind с токенами темы, установка shadcn/ui, Biome, структура папок по доменным модулям с запретом кросс-импортов между ними.

- ТЗ: 14.2
- Зависит: INF-01

# Интеграционные зависимости frontend

Все frontend-задачи выполнимы на моках MSW сразу после `FE-02`: реального backend для вёрстки и логики экранов не требуется. Таблица фиксирует, какой backend нужен каждой задаче для интеграционной приёмки — то есть для прогона её приёмочных сценариев против настоящего API, а не против мока.
