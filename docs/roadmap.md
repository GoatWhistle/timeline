# Roadmap — хакатоны, расписание, единая визуальная концепция

Отдельный от [todo.md](todo.md) список: тот ведёт рефакторинг и realtime,
этот — продуктовую работу, поставленную владельцем после команд и каталога.

**Как пользоваться.** `[ ]` не начато, `[~]` в работе, `[x]` сделано,
`[!]` заблокировано. Задача закрыта только вместе с миграцией или правкой
OpenAPI, тестами приёмочных сценариев и проходящим `make verify` — правило
[CLAUDE.md](../CLAUDE.md) и [dependency-order.md](dependency-order.md) раздел 5.

**Порядок исполнения — сверху вниз.** Этапы зависят друг от друга: цвет
хакатона нужен расписанию, карточка нужна и расписанию, и таблице, и плиткам,
а аудиты идут последними, потому что аудировать имеет смысл готовое.

**Максимум два агента одновременно.** Правило владельца. После каждого этапа —
коммит и push.

**Остановки нет: идут все четырнадцать этапов подряд.** Владелец снял
границу после этапа 9 и разрешил аудиты. Порядок сохраняется — аудиты
по-прежнему последние, потому что аудировать имеет смысл готовое.

**Push разрешён владельцем явно для всей этой работы.** Обычное правило
[CLAUDE.md](../CLAUDE.md) — «push делает владелец сам» — снято его
распоряжением на время выполнения этого плана. На работу за пределами
плана разрешение не распространяется.

## Этап 1. Создание хакатона: форма и календарь

Сейчас событие заводится через `features/event-list/admin`, отдельной формы
создания с человеческим выбором дат нет.

- [x] **1.** Полноценная форма создания и редактирования события: все поля
      ТЗ §14 (kind, format, origin, country_code, city, track, prize_pool,
      prize_currency, team_size_min/max, start_at, end_at, website_url).
      Валидация на клиенте повторяет серверную, но не заменяет её
- [x] **2.** Собственный календарь выбора даты вместо `<input type="date">`:
      клавиатура наравне с мышью, локализация ru/en, недели с понедельника,
      today/выбранное/недоступное различимы **не только цветом** (правило П2
      из аудитов todo.md)
- [x] **3.** Выбор диапазона `start_at` → `end_at` одним календарём с
      подсветкой промежутка. Правило `end_at > start_at` выражается в UI, а
      не только сообщением после отправки
- [x] **4.** Время отдельно от даты, с явной зоной. В базе всё в UTC;
      показывается в зоне пользователя. Расхождение «ввёл 10:00, сохранилось
      07:00» — дефект
- [x] **5.** Этапы (Stage) события в той же форме: добавление, удаление,
      порядок, собственный format этапа. От этого зависит вычисляемый
      `effective_format` (ТЗ §14)
- [x] **6.** `team_size_min <= team_size_max` проверяется в форме и на
      сервере; ноль и отрицательные отвергаются
- [x] **7.** Тесты приёмки формы: создание, правка, публикация, архивация,
      отказ по каждому правилу валидации. Каждая защита **проверяется
      мутацией**

## Этап 3. Цвет события

Владелец: «никогда два хака одного цвета не бывают», и российские отделены
от мировых.

- [ ] **14.** Палитра цветов событий в токенах, двумя семействами —
      `origin=RU` и `origin=WORLD`. Каждый цвет проверен на контраст в

- [ ] **15.** Назначение цвета при создании события. Хеш от id **не

- [ ] **16.** Поведение при исчерпании палитры описать явно: либо расширение
      палитры, либо переиспользование самого давнего. Молча выдавать
      дубликат нельзя — это прямо противоречит требованию
- [ ] **17.** Цвет отдаётся API вместе с событием и живёт в одном месте:

      каждый по-своему
- [ ] **18.** Цвет — никогда не единственный различитель (правило П2):

## Этап 8. Никнейм: два хвоста

- [ ] **38.** **Ник удалённого пользователя не освобождается.** Причина —
      несогласованность двух запросов в одном файле
      (`adapters/postgres/identity/nickname.go`): `GetByNickname` фильтрует
      `deleted_at IS NULL`, а `NicknameTaken` — нет. Живой человек получает
      «ник занят» на имя, которого никто не держит
- [ ] **39.** Механизм отложенного освобождения **уже построен** и его не
      надо изобретать: таблица `nickname_reservations` с `released_at`,
      `ReserveNickname`, `DropReservation`, `PurgeReservations`. Не хватает
      только связи с удалением аккаунта — при мягком удалении ник уходит
      в бронь на срок, потом освобождается
- [ ] **40.** Срок брони — параметр конфигурации, а не константа в коде
      (приложение C ТЗ). Смысл брони в том, чтобы чужой человек не занял
      ник сразу после удаления и не принял на себя чужую переписку
- [ ] **41.** Уникальный индекс `users_nickname_key` учитывает удалённых;
      решить и записать, снимается ли ник с удалённой строки или индекс
      становится частичным. Гонка «двое берут освободившийся ник» обязана
      разрешаться базой, а не проверкой перед вставкой
- [ ] **42.** **Ник становится обязательным в контракте, а не только в
      форме.** Сейчас `RegisterRequest` и `AcceptInviteRequest` принимают
      ник как необязательный: человек через сайт без ника не пройдёт, а
      прямой запрос к API создаст аккаунт без ника. Владелец хочет ник у
      всех, и командам он нужен для приглашений по нику — значит правило
      должно держать сервер. Ломается только наш собственный e2e-помощник
      `frontend/e2e/support/accounts.ts`; внешних клиентов у системы нет
- [ ] **43.** Существующие аккаунты без ника (все, созданные до правки:
      `nickname` не попадал в INSERT вовсе) — миграция данных либо запрос
      ника при следующем входе. Молча оставить половину базы без ника
      нельзя, иначе поиск по нику находит не всех
- [ ] **44.** Тесты: удаление освобождает ник по истечении брони, до
      истечения — не освобождает, регистрация без ника отвергается сервером,
      гонка двух заявок на один ник даёт `nickname_taken`

## Что помнить при исполнении

* **Максимум два агента одновременно.**
* Агентам git-операции не поручаются: коммит делает координатор после
  проверки. Один агент уже выполнил `git add` по всему дереву вопреки запрету
* `--update` у скриптов запрещён: он переписывает baseline и стирает пределы
* Комментариев нет нигде, русский — только в `docs/` и `locales/ru/*.json`
* Контракт раньше реализации: swag → `make back-docs` → `make types`
* Vite отдаёт устаревшие модули; при расхождении поведения и кода —
  `docker restart timeline-frontend-1` до начала отладки

## Этап 15. Полная проверка всех возможностей

Распоряжение владельца: после всех предыдущих этапов — **сплошная проверка
всего, что умеет система**, а не только того, что менялось последним.
Аудиты этапов 10–12 смотрят на код и на экран; этот этап смотрит на
поведение целиком, глазами человека, который системой пользуется.

- [ ] **62.** Сквозной проход по всем приёмочным сценариям ТЗ §19 —
      каждый выполняется руками в поднятом стеке и отмечается
      как пройденный или упавший. Не выборочно
- [ ] **63.** Каждая возможность из ТЗ §14 проверяется в обеих ролях:
      участник и администратор. Права проверяются с обеих сторон —
      что роль **может** и чего она **не может**
- [ ] **64.** Проверка всего, что добавлено этим планом: форма создания и
      календарь, обложки, цвет, расписание, карточка, каталог, пустые
      состояния, никнейм, язык и тема, команды с составами и приглашениями
- [ ] **65.** Уведомления (ТЗ §9, AC-NOTIF-01…19) — самое слабо покрытое
      место: конкурентный scheduler, отмена во время отправки, fallback
      канала, retry, восстановление после падения
- [ ] **66.** Обе темы и оба языка на каждом экране. Узкий экран наравне
      с широким. Клавиатура наравне с мышью
- [ ] **67.** Всё найденное закрепляется тестом, который **падает до
      починки**. Ненаблюдаемая находка — гипотеза, а не дефект
- [ ] **68.** Итог — отчёт владельцу: что проверено, что нашлось, что
      исправлено, что осталось. Без этого этап не закрыт
