# Часть 0. Имя системы

Система называется **Timeline**. Название используется везде: в интерфейсе,
в документации, в именах модулей и в названии репозитория.

## 0.1 Коллизия, которую надо развести

Слово уже занято внутри проекта. Сейчас `Timeline` — это **название экрана и
read-модели**: 15 упоминаний в ТЗ (раздел 11 «Timeline пользователя»,
«Admin Timeline», «Строка Timeline»), 118 в коде — `TimelineService`,
`my-timeline-page`, `admin-timeline-page`, `timeline.tsx`, endpoint-ы
`/timeline`.

Если тем же словом назвать всю систему, оно начнёт значить две разные вещи:
продукт целиком и один из его экранов. Это худший вид неоднозначности —
такой, где обе стороны выглядят правдоподобно.

## 0.2 Решение

**Имя системы — Timeline. Экран переименовывается.**

| Было | Стало |
|----|----|
| Система: Hackathon Tracker | Система: **Timeline** |
| Экран: Timeline пользователя | Экран: **Шкала** (англ. `Schedule`) |
| Экран: Admin Timeline | Экран: **Шкала администратора** |
| `modules/timeline/` | `features/schedule/` |

**Точный перечень символов backend.** `TimelineService` в коде **не
существует** — шкалу обслуживает `QueryService`. Реальная поверхность
переименования:

| Символ | Файл | Стало |
|----|----|----|
| `QueryController.MyTimeline` | `query_controller.go:101` | `MySchedule` |
| `QueryController.AdminTimeline` | `query_controller.go` | `AdminSchedule` |
| `QueryService.MyTimeline` / `AdminTimeline` | `deps.go:112-113` | `MySchedule` / `AdminSchedule` |
| `QueryRepository.TimelineRows` | `query_repo.go:184` | `ScheduleRows` |
| `models.TimelineFilter` | `dto_query.go` | `ScheduleFilter` |
| `models.TimelineResponse` / `TimelineRow` | `dto_query.go` | `ScheduleResponse` / `ScheduleRow` |

`QueryService` **не переименовывается**: он обслуживает не только шкалу, но и
«мои хакатоны» и запросы просрочки.

**Endpoint-ов два, а не один:**

| Было | Стало |
|----|----|
| `GET /api/v1/me/timeline` (`router.go:132`) | `GET /api/v1/me/schedule` |
| `GET /api/v1/admin/timeline` (`router.go:181`) | `GET /api/v1/admin/schedule` |

Одиночного `/api/v1/timeline` в системе нет.

### Порядок правки контракта

Переименование endpoint — **ломающее** изменение опубликованного контракта.
Псевдонимов старых путей не заводим: система до релиза. Порядок шагов
обязателен, иначе CI краснеет посреди этапа:

1. аннотации swag у контроллеров;
2. `make back-docs` — пересборка `swagger.yaml`/`json`;
3. `make types` — перегенерация `types.gen.ts`;
4. обработчики MSW в `frontend/src/mocks/handlers/`;
5. `contract.test.ts`;
6. один коммит целиком.

Обратное решение — оставить экран и придумать системе другое имя — отклонено,
потому что имя системы задано владельцем и обсуждению не подлежит. Значит
уступает то, что можно переименовать, а именно экран.

`Schedule` выбран потому, что описывает суть точнее: экран показывает
расписание этапов и дедлайнов. `Gantt` отклонён — термин отраслевой и
пользователю ничего не говорит.

## 0.3 Где меняется имя системы

| Место | Действие |
|----|----|
| `backend/go.mod` | `hackathon-os-backend` → `timeline-backend` |
| `frontend/package.json` | Имя пакета |
| Заголовок в интерфейсе, `<title>` | Timeline |
| README, ТЗ, backlog | Замена по тексту |
| Docker-образы, compose | Имена сервисов |
| Тексты уведомлений | Подпись отправителя |

Переименование модуля Go затрагивает каждый импорт в репозитории — делается
одной механической правкой, отдельным шагом, без совмещения с чем-либо ещё.

## 0.4 Как называть части

Внутри системы Timeline:

* **Каталог** — страница со всеми хакатонами;
* **Шкала** — страница с личным расписанием участия;
* **Карточка** — детальный вид одного хакатона;
* **Этап**, **контрольная точка**, **дедлайн** — объекты на шкале.

Слово «Timeline» в коде и текстах интерфейса больше **не обозначает экран**:
только систему. Проверяется линтером на запрещённые имена.

## I.9a Дефекты в текущей шкале

Найдены осмотром [timeline.tsx](../frontend/src/modules/timeline/timeline.tsx),
164 строки. Все подтверждены по коду.

| Место | Дефект |
|----|----|
| Строки 29–30 против 32 и 40 | `new Date(data.range.from)` создаёт новый объект на каждый рендер, а `useMemo` зависит от него. **Кэш не срабатывает никогда**: шкала и засечки пересчитываются каждый рендер. Мемоизация зависит от строк ISO, даты строятся внутри |
| Строка 111 | `const track = index % 2` — дорожка выбирается по чётности индекса, а не по пересечению. Два непересекающихся этапа разъезжаются на разные дорожки, а два пересекающихся с одинаковой чётностью накладываются. Отдельно показательно: комментарий строкой выше утверждает обратное — «пересечения раскладываются по двум дорожкам». **Комментарий лжёт**, и это довод в пользу чистки из раздела V.3 |
| Строки 116, 134 | `title={...}` — системная подсказка: задержка около 500 мс, не поддаётся оформлению, недоступна с сенсорного экрана и непоследовательно читается экранным диктором |
| Высота строки `h-16` | 64px при полосах на `top: 24 + track*20`. Две дорожки помещаются впритык, **три и больше обрежутся**. Значит высота чинится той же правкой, что и упаковка дорожек, а не отдельно |
| — | Линии «сегодня» нет вообще: главная опора шкалы отсутствует |
| Каждый этап — `<Link>` | Восемь этапов дают восемь одинаковых точек табуляции на один адрес. Для клавиатуры и диктора это мусор |
| Колонка названий | Не закреплена: при горизонтальной прокрутке названия хакатонов уезжают за край |

Отсюда важный вывод для раздела II.3a: шкалу **не надо переписывать с нуля** —
основа разумна. Надо исправить упаковку дорожек, мемоизацию, подсказки,
доступность и добавить линию «сегодня».

## I.9b Доступность нарушена на главном экране

`STAGE_TYPE_COLOR` — **единственный** признак типа этапа на полосе. Восемь
оттенков, часть из них близка по светлоте: `--stage-registration`
`oklch(0.48 0.14 250)` против `--stage-demo` `oklch(0.5 0.14 200)`. При
дальтонизме они сливаются.

Это нарушение WCAG 1.4.1 (использование цвета) прямо сейчас, на том экране,
который заявлен ядром продукта. Раздел 18 ТЗ требует WCAG 2.1 AA.

## I.9c Весь административный интерфейс грузится всем

`router.tsx` импортирует все страницы статически, без единого `lazy()`.
Из двадцати маршрутных компонентов **семь** закрыты `RequireAdmin`, и
участник, открывающий свою шкалу, всё равно скачивает управление
пользователями, приглашениями и журнал аудита.

Оговорка о величине выигрыша: административные экраны — в основном тонкие
таблицы. По собственным прикидкам раздела III.3c подрезка шрифтов даёт
больше (около 68 КБ), поэтому она тоже входит в срочные работы, а не только
разделение сборки.

## I.10 Модель не знает про географию

**Блокирующая находка.** В таблице `hackathons` нет ни одного поля
географии: `title`, `description`, `organizer`, `website_url`, `notes`,
`start_at`, `end_at`, `published_at`, `archived_at`. Разделение на «русские /
мировые / все» невозможно на фронтенде — это миграция и правка ТЗ, а не вопрос
вёрстки.

# Часть II. Целевая визуальная система

## II.0 Что мы делаем

Целевой продукт — **система управления участием в хакатонах**, и у неё две
стороны:

1. **Каталог** — много хакатонов, которые где-то существуют. Список либо
   плитка карточек, фильтры по географии и формату. Сюда же будет писать
   парсер. Задача: найти и решить, идти ли.
2. **Шкала** — те хакатоны, в которых уже участвуешь. Расписание этапов,
   контрольных точек и дедлайнов, как в TickTick. Задача: вести участие и
   ничего не пропустить.

Это **две разные страницы**, а не два режима одной. Причина не в оформлении:
у них разные данные и разные права.

| | Каталог | Шкала |
|----|----|----|
| Что показывает | Все опубликованные хакатоны | Только те, где пользователь `ASSIGNED` |
| Основа | Витрина, выбор | Инструмент, ведение |
| Форма | Список или плитка карточек | Расписание во времени |
| Единица | Хакатон целиком | Этап, контрольная точка, дедлайн |
| Права | Публичное чтение | Раздел 2 ТЗ: только свои назначения |

Смешать их в один экран нельзя: раздел 2 ТЗ прямо ограничивает пользователя
своими назначениями, и «показать все хакатоны в той же таблице, что и мои» —
это нарушение модели доступа, а не удобство.

Сейчас реализована только вторая сторона, и то частично. Каталог требует
модели географии (раздел II.3) и появляется вместе с ней.

Из существующих каталогов берётся приём фильтрации по географии; визуальных
решений оттуда не берём.

## II.1 Референсы

| Продукт | Что берём |
|----|----|
| TickTick | Оболочка, плотность, сохранённые виды в боковой панели, спокойная работа с датами |
| Linear | Система токенов и тёмная тема (раздел II.7), плотность, клавиатура, дисциплина цвета |
| Asana Timeline, Monday, ClickUp | Отрисовка полос, вех, линии «сегодня», уровней приближения |
| Notion Timeline, GitHub Projects | Группировка строк, поведение подписи в узкой полосе |
| Luma | Карточки событий и работа с таймзонами — пригодится для митапов |

Детальный разбор — раздел II.6, заполняется по результатам исследования.

## II.1a Две страницы

### Каталог

Маршрут `/catalog`. Все опубликованные неархивные хакатоны независимо от
участия.

**Два представления, переключаемых пользователем:**

* **Список** — плотные строки, по умолчанию. Название, даты, место, формат,
  дедлайн регистрации, состояние. Сканируется глазом сверху вниз, помещается
  много.
* **Плитка** — карточки в сетке, 3–4 колонки на 1440px, 2 на 1024px.
  Каждая карточка: название, организатор, даты, бейдж формата, город или
  «онлайн», срочность дедлайна, кнопка действия.

Выбор представления хранится в URL (`layout=list|grid`) наравне с фильтрами
и переживает перезагрузку. Плитка удобнее для просмотра «что вообще есть»,
список — для сравнения дат.

Фильтры каталога — по географии (`scope`), формату, датам, состоянию. Живут
в боковой панели как сохранённые виды (раздел II.3).

### Расхождения с ТЗ — обязательны к разрешению

Каталог задевает ТЗ сильнее, чем кажется, и это надо назвать прямо.

| Раздел ТЗ | Расхождение |
|----|----|
| 2 | В матрице прав нет анонимного лица вообще. Публичный каталог вводит **третий тип субъекта** сверх «Пользователь» и «Администратор» |
| 14.2 | «Публичных индексируемых страниц нет» — прямая посылка архитектуры, из которой выведен отказ от SSR. Публичный каталог делает её ложной |
| 5.1 | `hackathons.notes` видны только администратору. Новый путь чтения по той же таблице — ровно то место, где они утекут |

**Решения, без которых каталог не выпускается:**

* **Отдельное DTO каталога**, физически не способное нести `notes`. Не
  фильтрация на выходе, а другой тип — фильтр забывают, тип не забывается.
* **Ограничение частоты обязательно.** `adapters/ratelimit` уже есть и
  применяется к аутентификации. Неаутентифицированный список — самая дешёвая
  цель для выкачивания во всей системе.
* **Решение по индексации.** Раз «публичных страниц нет» больше не верно,
  нужен явный выбор: `robots.txt` с запретом или согласие на индексацию с
  соответствующими мета-тегами. Умолчания здесь нет.
* **Каталог может быть закрыт за входом.** Если анонимный доступ не нужен,
  все три расхождения исчезают. Это самый дешёвый вариант, и его стоит
  рассмотреть первым.

### Шкала

Маршрут `/schedule`. Только хакатоны, где пользователь `ASSIGNED`.
Расписание как основное представление (раздел II.3a), карточка хакатона в
третьей панели.

Это то, ради чего продукт существует, и то, что открывается по умолчанию
после входа. Каталог — вторичен: в него идут, когда ищут новое.

### Переход между ними

**Требует правки ТЗ, разделы 2 и 6 — см. часть IX.** Раздел 2 ТЗ прямо
относит добавление участников к правам администратора («Участники и
team_role | Нет | Добавление…»), а раздел 6 делает `team_role` обязательным
полем, которое при самозаписи некому заполнить.

Поэтому действие «участвую» **не реализуется до принятия решения**. Пока
открыто, из карточки каталога доступна только закладка (раздел IVc.6).
В обратную сторону перехода нет и не будет: удаление участия — операция
раздела 6 ТЗ, а не жест пользователя.

## II.2 Раскладка: три панели

```
┌──────────┬─────────────────────────┬──────────────────┐
│ Панель   │ Список / Шкала          │ Детали           │
│          │                         │                  │
│ Виды     │ строки хакатонов        │ карточка         │
│ Фильтры  │ плотные, 1 строка       │ этапы, статус    │
│          │                         │                  │
└──────────┴─────────────────────────┴──────────────────┘
  240px      flex                      380px, схлопывается
```

Третья панель открывается по клику на строку и не уводит с текущего списка —
как в TickTick. Фильтры живут в sidebar как сохранённые виды, а не в шапке
таблицы: их состояние переживает перезагрузку через URL (требование раздела
14.2 ТЗ).

## II.3 Виды: русские / мировые / все

Главная новая фича. Реализуется как **сохранённые виды в sidebar**, а не как
вкладки над таблицей: вкладки не масштабируются на будущие «митапы»,
«онлайн», «мои дедлайны», а список видов масштабируется.

Каждый вид — это именованный набор параметров URL, а не отдельный экран.
Один компонент списка, разные параметры:

| Вид | Параметры |
|----|----|
| Все | без фильтра области |
| Россия | `scope=RU` |
| Мир | `scope=INTL` |
| Онлайн | `format=ONLINE` |
| Мои | `assigned=me` |
| Ближайшие дедлайны | `deadline_within=7d`, сортировка по дедлайну |

### Модель географии

Требуется миграция. Предлагаемые поля `hackathons`:

**Две независимые категории**, а не одна. Их нельзя выводить друг из друга.

**Категория 1 — формат проведения:**

| Поле | Тип | Правило |
|----|----|----|
| `format` | enum `ONLINE` \| `OFFLINE` \| `HYBRID`, NOT NULL | Как проводится |
| `country_code` | `char(2)`, nullable | ISO 3166-1 alpha-2. **Обязателен при `OFFLINE` и `HYBRID`** — для гибрида это страна финала |
| `city` | `text`, nullable | Город площадки, отображение в карточке |

Для `HYBRID` указывается страна финала: очная часть где-то происходит, и
именно она определяет, куда ехать.

Ограничение выражается в базе: `CHECK (format = 'ONLINE' OR country_code IS
NOT NULL)`. Иначе появится офлайновый хакатон без места.

**Категория 2 — чей хакатон:**

| Поле | Тип | Правило |
|----|----|----|
| `origin` | enum `RU` \| `WORLD`, NOT NULL | Российский или мировой |

Умолчание для существующих строк — `RU`.

Хранится отдельно и **не выводится из `country_code`**: международный
хакатон с финалом в Москве по географии российский, а по происхождению
мировой. Правило «`country_code = RU` → российский» ложно, и вычислять его
на лету значит зашить ошибку в запрос.

**Виды строятся по этим двум полям:**

| Вид | Условие |
|----|----|
| Все | Без фильтра |
| Россия 🇷🇺 | `origin = 'RU'` |
| Мир 🌍 | `origin = 'WORLD'` |
| Онлайн | `format = 'ONLINE'` |
| Очные | `format IN ('OFFLINE', 'HYBRID')` |

Первые три взаимоисключающи — это сегментный переключатель. Фильтр по
формату применяется поверх и живёт отдельным элементом.

### Митапы — в прайм-версии, не «когда-нибудь»

Митапы делаются сразу. Решение о том, как именно:

**Отдельная сущность не заводится.** Добавляется `kind` enum
`HACKATHON` | `MEETUP` в ту же таблицу: у митапа те же даты, площадка,
регистрация и дедлайн. Разделение на две таблицы удвоило бы участие,
уведомления и шкалу ради разницы в одном слове.

### `hackathon` → `event` во всей системе

**Сущность переименовывается.** Раз в одной таблице живут два вида событий,
называть её `hackathons` — значит закрепить в схеме ложь: половина строк
хакатонами не будет. Имя `event` честно описывает, что там лежит.

Объём: 106 файлов кода, 17 внешних ключей `hackathon_id`, составные
ограничения целостности раздела 8 ТЗ. Это много, но проект небольшой, и цена
неверного имени в основании модели выше цены механической правки. Чем позже
переименовывать, тем дороже.

| Было | Стало |
|----|----|
| Таблица `hackathons` | `events` |
| `hackathon_id` (17 ключей) | `event_id` |
| `hackathon_participants` | `event_participants` |
| `hackathon_end_at` в `registrations` | `event_end_at` |
| `Hackathon`, `HackathonState` | `Event`, `EventState` |
| `HackathonService`, `HackathonRepository` | `EventService`, `EventRepository` |
| `/api/v1/hackathons` | `/api/v1/events` |
| `modules/hackathons/` | `entities/event/`, `features/event-*/` |
| «Мои хакатоны» | «Мои события» |

**Что требует особой осторожности.** Составные ограничения раздела 8 ТЗ
завязаны на эти имена и держат правила, которые обычный `CHECK` не выражает:

* `UNIQUE(id, end_at)` на событии и составной внешний ключ
  `(event_id, event_end_at)` с `ON UPDATE CASCADE` — держит
  `deadline_at ≤ end_at`;
* денормализованный `event_id` в `registration_statuses` — держит
  межсобытийную целостность.

Переименовать их можно, ослабить нельзя. После правки миграций
интеграционный тест ограничений (`constraints_integration_test.go`) обязан
проходить без изменения смысла проверок — он и есть доказательство, что
правила уцелели.

**Слово «хакатон» остаётся** там, где речь именно о хакатоне: `kind =
HACKATHON`, подписи в интерфейсе, тексты уведомлений о конкретном событии.
Переименование касается контейнера, а не вида.

### Чем митап отличается от хакатона

Различия невелики, и это подтверждает решение о единой таблице:

| | Хакатон | Митап |
|----|----|----|
| Длительность | Дни | Часы, обычно вечер |
| Этапы | Много, с контрольными точками | Один или ни одного |
| Регистрация | С дедлайном | Обычно с дедлайном |
| Команда | Есть `team_role` | Роли нет, `team_role` необязателен |
| Результат | Место, приз | Нет |

Отсюда два следствия:

* **`team_role` становится необязательным при `event_kind = MEETUP`.**
  Сейчас раздел 6 ТЗ делает его обязательным всегда. Правится тем же
  изменением, что и самозапись, — там `team_role` тоже требует пересмотра.
* **Митап короче суток**, а этап хакатона измеряется днями. Это и есть тот
  случай, ради которого нужна почасовая сетка (вопрос Б5): на шкале с
  масштабом «неделя» вечерний митап схлопнется в вертикальную чёрточку.
  Решение: митап рисуется **моментом** — ромбом, как контрольная точка, а не
  полосой. Тогда почасовая сетка не нужна вовсе, и вопрос Б5 закрывается.

## II.3a Шкала — ядро продукта

Главный экран, а не вспомогательный. Раздел 14.2 ТЗ уже предписывает свой
компонент на CSS Grid плюс `d3-scale` — решение правильное, но нынешняя
реализация показывает только интервалы этапов и маркер дедлайна. Нужен
инструмент, по которому видно состояние участия одним взглядом.

### Модель из календаря TickTick: полоса поверх сетки дней

Прямой референс — календарь TickTick, где **многодневное событие рисуется
сплошной полосой поверх сетки дней**, отдельной зоной над почасовой сеткой.
Полоса начинается в своём дне, кончается в своём и не разрывается на границе
суток.

Это и есть нужная модель. Хакатон длится дни и недели, поэтому:

* **главное — зона многодневных полос**, а не почасовая сетка: у этапа
  хакатона есть день начала и день конца, а не время «09:00». Почасовая
  часть календаря нужна там, где событие короче суток — этот вопрос
  открыт, см. раздел IX;
* зона многодневных полос занимает всю шкалу, а не узкую ленту сверху;
* полоса, выходящая за границу видимого диапазона, обрезается плоским краем
  вместо скруглённого — признак того, что она продолжается за экраном.

Из того же скриншота берутся два приёма:

* **Цвет как код категории.** Каждая полоса залита своим цветом, подпись
  внутри полосы. У нас цвет кодирует тип этапа — палитра из восьми типов уже
  есть в токенах.
* **Текущий день выделен цветом числа**, а не заливкой ячейки. Дешевле по
  вниманию и не конфликтует с цветными полосами.

Отличие от TickTick: там строка это день, а событий много. У нас строка это
**хакатон**, а по горизонтали идёт время. Иначе два параллельных хакатона
слиплись бы в одну ленту, чего раздел 11 ТЗ прямо не допускает.

### Три типа объектов на одной строке

Это ключевая задача отрисовки: на одной строке живут вещи разной природы, и
их нельзя рисовать одинаково.

| Объект | Природа | Отрисовка |
|----|----|----|
| Этап | Интервал | Полоса 30px, скругление 3px, заливка по типу этапа |
| Этап без дат | Интервал-догадка | Прозрачная заливка, пунктирная обводка |
| Контрольная точка | Момент | Ромб 10–12px, фиксированный размер, поверх полос |
| Дедлайн регистрации | Момент, критичный | Заполненный ромб плюс засечка, цвет по срочности |
| Сегодня | Момент, глобальный | Линия 1px + кружок 6×6 сверху + плашка в шапке |

Шаг строки 48px: полоса 30px плюс по 18px отступа. Пропорции взяты из
Frappe Gantt (раздел II.6), где они выверены на практике.

**Момент не рисуется полосой нулевой ширины** — он исчезнет. Ромб имеет
фиксированный пиксельный размер и **не масштабируется вместе со шкалой**:
однодневная полоса при масштабе «квартал» превращается в 4px и пропадает, а
ромб виден на любом приближении. Это главная причина, по которой веха
рисуется другой фигурой, а не узкой полосой.

Ромб получает обводку 1–2px цветом фона строки, чтобы оставаться читаемым,
когда попадает поверх полосы этапа.

Различение по заливке: **заполненный ромб — мой дедлайн** (требуется
действие), **полый — веха организатора** (просто происходит).

### Приближение

**Три уровня: неделя, месяц, квартал.** Изначально планировалось четыре;
сокращено по примеру GitHub Projects — семь уровней нужны библиотеке, а не
продукту, и каждый лишний уровень это ещё один набор правил отрисовки
подписей. ТЗ требует минимум месяц и неделю, оба на месте.

Переключатель масштаба стоит вплотную к кнопке «Сегодня» (приём Notion):
эти два действия всегда нужны вместе. Состояние сохраняется в URL наравне с
фильтрами.

Вокруг диапазона данных рисуется запас пустого времени, чтобы полосы не
упирались в край экрана.

**Подпись в узкой полосе** — поведение копируется дословно: пока подпись
помещается, она по центру внутри полосы; как только не помещается, уходит
вправо за край полосы с отступом 5px и меняет цвет на основной. У полосы,
частично уехавшей за край экрана, подпись скользит вдоль неё и остаётся
видимой. Обрезать многоточием посреди слова хуже, чем сдвинуть.

### Одна подсвеченная точка

Приём Linear: **ровно одна контрольная точка выделена** как ближайшая
предстоящая. Не радуга статусов у всех вех, а один акцент фокуса. Самый
дешёвый способ ответить на вопрос «что дальше» без чтения дат.

### Прогресс по этапам

Отдельный индикатор в карточке: горизонтальный степпер по этапам хакатона с
отметкой текущего. Он отвечает на вопрос «где я сейчас» без чтения дат — то,
ради чего продукт существует. Пройденные этапы приглушены, текущий выделен
акцентом, будущие нейтральны.

Рекомендованный предел степпера — 3–6 шагов, и число этапов хакатона в него
укладывается естественно. Подпись «Этап 2 из 4» рядом.

Показывается **оставшееся время**, а не пройденное: оставшееся подталкивает
к действию, пройденное годится там, где важен набранный ход.

Определяется вычислением от текущего времени, а не хранится: раздел 5.2 ТЗ
прямо говорит, что у этапа нет скрытого бизнес-состояния, и заводить его
нельзя.

### Цвет не должен быть единственным признаком

Раздел I.9b: сейчас тип этапа закодирован **только** цветом, и это нарушение
WCAG 1.4.1 на главном экране. Нужны дублирующие каналы:

1. **Подпись** — уже есть, но пропадает на узкой полосе;
2. **Значок типа этапа** при ширине больше 24px. `lucide-react` уже в
   зависимостях: регистрация — список, отбор — фильтр, участие — люди,
   контрольная точка — флаг, сдача — стрелка вверх, демо — экран,
   результаты — кубок;
3. **Штриховка** для трёх самых близких по цвету типов — повторяющийся
   градиент под 45° с прозрачностью 10% поверх заливки, лишнего узла не
   требует;
4. **Форма** отделяет момент от интервала сама по себе: прямоугольник против
   ромба.

Для статуса регистрации и срочности — то же правило. Срочность лучше всего
передаётся **числом**: «осталось 2 дня», «просрочен на 1 день». Относительное
время — самый надёжный нецветовой признак срочности.

Проверка: снимок экрана через `filter: grayscale(1)` в Playwright и
утверждение, что все объекты по-прежнему различимы.

### Доступность: шкала — это таблица

Не изобретать схему ARIA. Для экранного диктора шкала — **таблица**: строка
на хакатон, в ячейке связное предложение, а не координаты:

> «Хакатон Х. Идёт. Четыре этапа: регистрация 1–10 марта, отбор 11–15 марта,
> участие 16–18 марта, результаты 20 марта. Дедлайн регистрации 9 марта,
> осталось 2 дня. Регистрация не отмечена.»

Одно такое предложение полезнее любого количества ARIA на отдельных полосах.

**Одна точка табуляции на строку** вместо восьми (дефект из I.9a), дальше —
клавиши:

| Клавиша | Действие |
|----|----|
| `→` `←` | Следующий и предыдущий объект в строке по времени |
| `↑` `↓` | Та же позиция во времени, соседняя строка |
| `Home` `End` | Первый и последний объект строки |
| `Enter` | Открыть |
| `+` `-` | Приблизить и отдалить |
| `t` | К сегодняшнему дню |

При переходе фокуса область `aria-live="polite"` объявляет объект.
**Задержка объявления 150 мс**, иначе удержание стрелки поставит в очередь
три десятка реплик.

**Фокус должен быть виден на восьми разных заливках.** Двойное кольцо:
`outline` цветом фокуса плюс `box-shadow` цветом фона. Это гарантирует
контраст на любой полосе.

### Как это построено

**Остаёмся на DOM.** Тяга взять canvas — главная ловушка этого раздела.
Canvas отнимает доступность целиком, требует параллельного дерева для
диктора и фокуса, ручного попадания курсором и чтения токенов темы через
`getComputedStyle`. При наших объёмах (раздел 18 ТЗ: 100 неархивных
хакатонов) DOM справляется с запасом. Порог для пересмотра — тысячи объектов
одновременно.

**Упаковка дорожек** вместо `index % 2`: сортировка по началу, поиск первой
дорожки, где предыдущий объект закончился раньше начала текущего с зазором.
Считать в **пикселях, а не во времени**: два часовых этапа в разных днях при
масштабе года отрисуются в двух пикселях друг от друга. Высота строки растёт
от числа дорожек.

**Попадание по моменту.** Дедлайн шириной 2px курсором не поймать. Невидимая
область попадания 20px вокруг через псевдоэлемент — лишнего узла не нужно.
Моменты лежат слоем выше интервалов.

**Линия «сегодня» без перерисовки каждую секунду.** Позиция пишется в
переменную CSS напрямую из таймера, минуя состояние React: перерисовок ноль.
Частота зависит от масштаба — при масштабе месяца пиксель это около
двенадцати минут, обновлять чаще минуты бессмысленно. Таймер
останавливается, когда вкладка скрыта, и пересчитывается при возврате: ноутбук,
открытый через шесть часов, не должен показывать вчерашнюю линию.

Сама линия **не анимируется**: плавно ползущая линия «сейчас» читается как
дефект.

**Приближение анимируется через область значений**, а не через DOM: шкала —
чистая функция от начала, конца и ширины. Интерполяция по логарифму, чтобы
шаг колеса ощущался одинаково на любом масштабе.

### Узкий экран

Минимум по разделу 18 ТЗ — 1024px, но шкала должна вести себя разумно и
уже.

**Левая колонка с названиями замораживается, время прокручивается
горизонтально.** Это главный приём: без него строка теряет опознание.
Горизонтальная прокрутка широкой шкалы нормальна и ожидаема — впихивать
квартал в узкий экран не нужно.

Ниже примерно 760px подписи полос переезжают **над** полосы, а не внутрь.
Если места нет и на это, шкала схлопывается не в список, а в **вертикальный
степпер** на хакатон — этапы сверху вниз с отметкой текущего.

### Пересечения

Раздел 11 ТЗ разрешает пересекающиеся этапы. Строка остаётся одной на
хакатон, пересекающиеся полосы раскладываются на дорожки внутри строки, и
высота строки растёт. Схлопывать пересечения в одну полосу нельзя — потеряется
факт параллельных этапов.

## II.4 Темы: светлая и тёмная

Обе темы полноценные и равноправные — тёмная не «вариант», а основная по
духу системы Linear.

Механика частично есть: `@custom-variant dark (&:is(.dark *))` и наборы
токенов. Что добавляется:

**Переключатель на три состояния** — светлая, тёмная, системная. Системная
по умолчанию: браузер уже знает предпочтение пользователя, спрашивать заново
невежливо.

**Защита от мигания.** Выбор хранится в `localStorage` и применяется
блокирующим скриптом в `<head>` до первой отрисовки. Без этого при каждой
загрузке мигнёт светлая тема — самый заметный дефект тёмного интерфейса.

**Место хранения.** Для авторизованного — в профиле (`users.theme`), чтобы
переносилось между устройствами; `localStorage` как кэш и как единственный
источник для неавторизованного.

**Проверка контраста автоматическая.** Раздел 18 ТЗ требует WCAG 2.1 AA, и
проверять две темы глазами нереально: пар «фон / текст» больше сотни с учётом
восьми типов этапов и пяти уровней срочности. Проверка в тестах через axe,
обе темы, на критических экранах.

**Что переключается вместе с темой:** все семантические и доменные токены,
включая акцент (раздел II.7), палитру типов этапов и шкалу срочности. Цвета
не должны определяться нигде, кроме `tokens/*`.

Палитра и шкала — раздел II.7.

## II.4a Шрифты

Сейчас шрифтов нет **вообще**: ни файлов, ни `@font-face`, ни `font-family`.
Интерфейс отрисовывается системным шрифтом, у каждого пользователя своим.
При этом в `reset.css` стоит `font-feature-settings: "cv11"` — настройка
альтернативной одноэтажной `a` из Inter, которой в проекте нет. То есть
строка не влияет ни на что.

### Требования к выбору

Свои шрифты, скачанные локально. Не системные и не «первое, что все берут».

Обязательные условия — гарнитура отпадает, если не выполнено любое:

1. **Кириллица, нарисованная автором**, а не выведенная автоматически.
   Интерфейс на двух языках, и русский обязан выглядеть так же намеренно,
   как английский. Это условие отсекает большинство модных гарнитур.
2. **Свободная лицензия** для коммерческого использования.
3. **Переменное начертание** — система из [tokens.md](tokens.md) стоит на
   весах 400 / 510 / 590, статическими начертаниями 510 не получить.
4. **Пригодность к самостоятельному размещению** — файлы скачиваются, а не
   подключаются с чужого домена.
5. **Читаемость на 12–15px** с плотным трекингом: это плотный рабочий
   интерфейс, а не витрина.

**Inter не берём как основной.** Он затёрт до состояния значения по
умолчанию: Linear, Vercel и половина продуктов выглядят одинаково. Условиям
он удовлетворяет, поэтому годится как мерило для сравнения, но узнаваемости
продукту не добавит.

### Выбор: Geist Sans и Geist Mono

Проверено измерением бинарников, а не по описаниям.

| Проверка | Sans | Mono |
|----|----|----|
| Русские буквы | 64 из 64 | 64 из 64 |
| `Ё`, `№` | есть | есть |
| Ось веса | 100–900 | 100–900 |
| Единиц на кегль | 1000 | 1000 |
| Восходящий / нисходящий | 1005 / −295 | 1005 / −295 |
| Высота строчных | 53.0% | 53.0% |
| Поднабор кириллицы | 15 КБ | 13 КБ |

**Метрики совпадают до единицы** — это и есть главный довод за пару.
Моноширинная метка времени садится на ту же базовую линию и в тот же
оптический размер, что и русская подпись рядом, без единой подгонки. У пар
из разных мастерских так не бывает: там высоты строчных расходятся, и
приходится править `font-size-adjust` вручную.

Одни авторы, один рисунок кириллицы, одинаковое покрытие в обоих файлах.

**Про кириллицу Geist.** Распространённое «у Geist её нет» устарело: она
появилась в версии 1.7.0 и **нарисована заново**, а не выведена из латиницы.
Страница Fontsource и файл README до сих пор описывают гарнитуру как
латинскую, поэтому почти все ответы в сети неверны. Проверяется за минуту:
скачать поднабор и посмотреть таблицу символов.

Что это даёт по существу:

* веса 400 / 510 / 590 из [tokens.md](tokens.md) берутся напрямую с оси;
* у Sans есть табличные цифры (`tnum`) — колонки чисел выравниваются;
* у Mono перечёркнутый ноль **по умолчанию** — то, что нужно для
  идентификаторов в журнале аудита;
* лицензия SIL OFL 1.1 прописана в самом файле;
* весь набор из двух гарнитур и двух письменностей — около 79 КБ.

Характер: геометричный неогротеск, тихий и плотный, ровно под такую
поверхность. Известен, но с кириллицей его почти никто не применял — то есть
не выглядит дежурным выбором.

**Что проверить перед тем, как закрепить.** Кириллица моложе латиницы,
поэтому смотрим её в деле: самая плотная русская таблица на 12 и 13 px в
обеих темах. И отдельно — трекинг: у кириллицы ритм вертикальных штрихов
(`и`, `ш`, `щ`, `ц`) сбивается при плотной посадке раньше латиницы, поэтому
отрицательный трекинг для русского берётся мягче.

### Слабое место Geist: ширина плывёт при смене веса

Замерено на строке «Регистрация участника Registration»:

| Гарнитура | 400 → 590 |
|----|----|
| Geist | **+3.85%** |
| Golos Text | +1.41% |
| PT Root UI (по внешнему замеру) | 0.00% |

Значит подсветка строки или наведение, меняющие вес с 400 на 510, **сдвигают
разметку**. Для плотной таблицы это заметно.

**Решение — не менять вес там, где это сдвинет соседей.** Состояние
показывается цветом, фоном и значком, а вес меняется только там, где справа
пусто: заголовки, отдельно стоящие подписи. Приём общий: раздел II.7
запрещает нести смысл одним цветом, здесь симметрично — не нести состояние
одной толщиной.

Если на практике окажется, что без смены веса не обойтись, есть запасной
вариант — **Golos Text** (Кабанова, Кузьмин, Paratype, OFL): дрейф втрое
меньше, кириллица родная. Его ограничение — ось от 400, легче не бывает, и
у гарнитуры сильная ассоциация с государственными сервисами.

**PT Root UI** равноширинный по построению и потому идеален для такой задачи,
но **его нет на Fontsource** (ответ 404), а официальная сборка недоступна по
прямой ссылке. Брать его — значит собирать и хранить файл вручную. Если
дрейф Geist окажется проблемой на деле, это первый кандидат на замену.

### Моноширинный: проверка и оговорки

Отдельно проверены кандидаты на моноширинный. Geist Mono подтверждён, но у
него есть один изъян и несколько соседей, которые отпали по существу.

**Символов клавиш в Geist Mono нет** — проверено: ни `⌘`, ни `⌥`, ни `⌃`,
ни `⇧`. Для нас это не помеха: приложение — настольный веб, а не программа
для macOS, и сочетания подписываются словами (`Ctrl+K`). Если когда-нибудь
понадобятся значки модификаторов, единственный кандидат с ними —
JetBrains Mono.

**Ноль у Geist Mono перечёркнут по умолчанию**, причём `ss09` его убирает —
логика обратная привычной. Для идентификаторов в журнале аудита умолчание
как раз верное, трогать не нужно.

Отпавшие, чтобы не возвращаться к ним:

| Гарнитура | Причина |
|----|----|
| Commit Mono, Recursive, Intel One Mono, Space Mono | Кириллицы нет вовсе |
| Iosevka | Лучшая кириллица и плотность, но **переменной сборки не существует** — вес 510 недостижим |
| Roboto Mono | **Ноль неотличим от `O`**: таблица подстановок пуста, начертание одно. Для идентификаторов это дисквалификация |
| Fira Code | Лигатуры `->` портят идентификаторы |
| Martian Mono | По умолчанию самый широкий — плохо для колонок времени, требует явной настройки оси ширины |

**Ловушка Fontsource:** файлы `recursive-cyrillic-ext-*.woff2` там есть, но
кириллических символов внутри ноль. Подключение по `unicode-range` даст
пустые квадраты вместо букв. Ещё один довод за то, чтобы проверять
бинарники, а не описания.

### Подрезать самим, а не брать готовые поднаборы

Проверено: в кириллических поднаборах Fontsource **нет `tnum`** — ни у
Geist, ни у Golos. Табличные цифры нужны для колонок времени и чисел, значит
поднаборы собираются самостоятельно из полного файла с явным перечислением
нужных возможностей:

```
python -m fontTools.subset Geist-Variable.woff2   --unicodes="U+0000-00FF,U+2000-206F,U+2116,U+0400-045F,U+0490-0491"   --layout-features="kern,ccmp,locl,tnum,case,liga"   --flavor=woff2 --output-file=geist-cyr.woff2
```

Без `--instance`: он схлопнет переменную ось, и вес 510 станет недоступен.

### Отвергнутые варианты

Не по вкусу, а по измеренным причинам:

| Гарнитура | Причина отказа |
|----|----|
| IBM Plex Mono | **Переменной версии не существует**, только статические начертания |
| Golos Text | Ось веса 400–900: легче 400 нет, и наш диапазон лежит у самого края |
| Wix Madefor Text | То же ограничение снизу плюс самая низкая высота строчных (49.2%) |
| Fira Code | Ось 300–700, кириллица в переменной сборке грубее |
| Rubik | Ось 300–900 и сильно затёрт в русском вебе |
| Commissioner | Высота строчных 49.4% — мало для 12–15 px |
| Onest | Достойный запасной вариант: кириллица родная, но нет `tnum` и нет парного моноширинного |
| Martian Mono | Широкий по построению — плохо для колонок времени |

### Моноширинный — тоже свой

Нужен для времени в UTC, идентификаторов в журнале аудита и сочетаний
клавиш: там важно, чтобы цифры стояли колонкой.

Системный `ui-monospace` не подходит: он разный на разных машинах, и
выравнивание колонок перестаёт быть предсказуемым. Berkeley Mono из
`tokens.md` отпадает по лицензии.

Берётся **Geist Mono** — из того же семейства, с теми же метриками и тем же
рисунком кириллицы.

### Только локальные файлы

**Google Fonts не используется.** Причины по убыванию важности:

1. Сторонний домен в критическом пути отрисовки: пока он отвечает, текста
   нет;
2. запрос к чужому серверу с каждого экрана пользователя — вопрос, которого
   у внутренней системы быть не должно;
3. лишнее соединение и разрешение имени на первой загрузке.

Файлы кладутся в `frontend/public/fonts/` и раздаются с того же origin, что
и приложение.

### Подрезка обязательна

Переменная гарнитура со всеми письменностями — сотни килобайт. Подрезка до
двух нужных наборов обязательна:

| Файл | Латиница | Кириллица |
|----|----|----|
| Geist Sans | 28.7 КБ | 14.7 КБ |
| Geist Mono | 22.6 КБ | 12.6 КБ |
| **Итого** | | **~79 КБ** |

Это больше, чем даёт разделение сборки по маршрутам (раздел I.9c), и потому
входит в срочные работы.

**Оба поднабора грузятся сразу**, а не по языку: переключение языка не должно
ждать загрузки шрифта, а 42 КБ того не стоят. Разделение на `unicode-range`
оставляем — браузер сам не скачает кириллицу, пока она не понадобится, если
на странице только латиница.

### Правила подключения

* `font-display: swap` — текст виден сразу запасным шрифтом;
* `<link rel="preload">` только на **основной вес**; предзагрузка всех
  начертаний забивает канал ровно тогда, когда он нужен разметке;
* **запасной шрифт с подгонкой метрик** — `size-adjust`, `ascent-override`,
  `descent-override`. Без этого при подмене шрифта страница дёргается, и
  показатель сдвига вёрстки портится именно на первой загрузке;
* запасная цепочка заканчивается системным шрифтом, а не `sans-serif`.

### Проверка

Шрифт должен проверяться, а не приниматься на веру:

* тест, что оба поднабора существуют и подключены;
* снимок экрана с кириллицей и латиницей в обеих темах — русский текст на
  15–20% длиннее, и это единственный способ увидеть, что раскладка выдержала;
* проверка, что внешних запросов к шрифтовым доменам нет.

## II.5 Плотность и типографика

Правило: интерфейс рабочий, не маркетинговый. Строка списка — одна строка, а
не карточка на пол-экрана.

| Уровень | Размер | Начертание | Применение |
|----|----|----|----|
| Заголовок экрана | 20px | 600 | один на экран |
| Заголовок секции | 15px | 600 | карточки, вкладки |
| Основной текст | 14px | 400 | строки списков, поля |
| Вторичный | 13px | 400 | даты, организатор, счётчики |
| Подпись | 12px | 500 | бейджи, метки колонок |

Высота строки списка 36–40px. Вертикальный ритм кратен 4px.

Цвет несёт смысл: состояние хакатона, статус регистрации, срочность дедлайна,
тип этапа. Всё остальное — оттенки серого. Акцентный цвет только у активного
элемента и первичной кнопки.

### Срочность дедлайна

Отдельная шкала, потому что это главное, ради чего продукт существует:

| Состояние | Условие | Цвет |
|----|----|----|
| Спокойно | > 7 дней | вторичный текст, без выделения |
| Скоро | 1–7 дней | `--status-todo` (янтарный) |
| Сегодня | < 24 часов | янтарный, начертание 600 |
| Просрочено | дедлайн прошёл, статус TODO | `--destructive` |
| Готово | статус DONE | `--status-done`, приглушённо |

Срочность вычисляется на клиенте от времени показа. Это отображение, а не
доменное состояние: раздел 8 ТЗ знает только `TODO`/`DONE`/`NOT_REQUIRED`, и
добавлять «просрочено» в статус нельзя.

## II.6 Разбор референсов

Числа взяты из опубликованных систем и исходников, а не на глаз.

### Frappe Gantt — готовая геометрия

Самый полезный источник: открытая реализация с точными значениями и парой
токенов для обеих тем.

| Параметр | Значение |
|----|----|
| Высота полосы | 30px |
| Вертикальный отступ строки | 18px, шаг строки 48px |
| Скругление полосы | 3px |
| Высота шапки | 45px |
| Ширина колонки | 140px неделя, 120px месяц |

**Маркер «сегодня» — составной из трёх частей**, а не одна линия:

1. вертикальная линия 1px во всю высоту сетки, `z-index: 999`;
2. кружок 6×6px, венчающий линию сверху (`top: высота шапки − 6`);
3. сегодняшнее число в шапке инвертируется — заливка, светлый текст,
   скругление 5px.

Именно кружок и инвертированная плашка делают линию осмысленной, а не
похожей на случайную границу. Цвет «сегодня» в светлой теме — почти чёрный
`#37352f`, **не красный**: красный зарезервирован за просрочкой.

**Правило подписи в узкой полосе** — точная логика из исходника: пока
подпись помещается, она по центру внутри полосы; как только ширина подписи
превышает ширину полосы, подпись уходит вправо за край с отступом 5px и
меняет цвет на тёмный. Отдельно: у полосы, частично уехавшей за левый край
экрана, подпись скользит вдоль неё и остаётся видимой.

**Прогресс** рисуется вложенным прямоугольником, а не прозрачностью. Есть
отдельный «ожидаемый прогресс» — призрак того, где следовало быть.

**Полоса без подтверждённых дат:** прозрачная заливка, пунктирная обводка
`stroke-dasharray: 5`. Готовый ответ для этапа с неизвестными датами.

### Linear — вехи и дисциплина

* Вехи — **ромбы**, вид меняется по проценту выполнения.
* **Ровно одна веха подсвечена** как «то, к чему идём сейчас». Дешёвый и
  сильный приём: не радуга статусов, а один акцент фокуса.
* Цвет означает риск срыва и он **двоичный**: нейтральный — даты есть,
  красный — срок нарушен или будет нарушен. Никаких зелёно-жёлто-красных
  градиентов.
* Высота подъёма — лестница поверхностей плюс границы 1px, **теней нет
  вообще**.
* Принцип: «структура должна чувствоваться, а не быть видимой» — боковая
  панель намеренно на несколько ступеней тусклее содержимого.

### GitHub Projects — сдержанность в приближении

**Ровно три уровня: месяц, квартал, год.** Семь уровней — проблема
библиотеки, а не продукта. У нас набор сдвинут на ступень вниз — неделя,
месяц, квартал, — потому что раздел 14.2 ТЗ прямо требует масштабы месяца и
недели. Плюс отдельный переключатель вертикальных
маркеров: маркеры это линии сквозь все строки, они отделены от полос строк.
Это ровно наша модель «дедлайн хакатона» против «полоса этапа».

### Notion — связка приближения и «сегодня»

Переключатель масштаба стоит вплотную к кнопке «Сегодня». Два действия,
которые всегда нужны вместе, собраны в один узел.

### TickTick — оболочка

* Акцент `#4772FA`, один синий. Замер по странице: **21 употребление акцента
  против 701 почти-чёрного** — вот что значит «цвет экономно».
* Иерархия текста — **лестница прозрачности одной краски**, а не разные
  серые: 1.0 / 0.8 / 0.6 от `rgb(25,25,25)`. Поэтому тёмная тема получается
  инверсией краски, а не второй палитрой.
* Три панели, правая появляется только при выборе.
* Умные списки в боковой панели, цвет и эмодзи у списка для быстрого поиска
  глазом.
* Известная слабость, которую надо избежать: панель «переполняется» без
  дисциплины. Число видов ограничивать.

### Luma — время и события

* **Часы с зоной в глобальной шапке** (`19:18 GMT+3`) — зона объявляется
  один раз, а не подписывается у каждой строки.
* Даты «сначала относительно, потом абсолютно»: `Сегодня, 18:30` →
  `Ср, 2 сен, 18:00`. День недели всегда, кроме сегодня.
* Дата — 14px, обычное начертание, краска на 36% — **приглушена и стоит над
  названием**, которое, наоборот, жирнее.
* Порядок в карточке: время → название → место.

### Каталоги: чему не следовать

У Devpost плашка срочности **одного цвета при любом остатке** — «4 дня» и
«около месяца» выглядят одинаково. Раз срочность это смысл нашего продукта,
здесь надо делать ровно наоборот и эскалировать (раздел II.5).

Из каталогов берётся только модель фильтров: у MLH регион — сегментный
переключатель на три значения, у Devpost отдельные группы «место»,
«состояние», «длительность» и счётчик активных фильтров со сбросом.

### Переключатель видов: сегментный, а не вкладки

Правило разделения: **вкладки меняют раздел, сегментный переключатель меняет
охват тех же данных**. «Россия / Весь мир / Все» — три взаимоисключающих
охвата над одними данными, то есть сегментный переключатель, и три значения
укладываются в рекомендованные 2–5.

Отсюда уточнение раздела II.3: сегментный переключатель охвата стоит в шапке
списка, а сохранённые виды остаются в боковой панели. Переключатель формы
(список / плитка / шкала) — отдельный значковый узел справа сверху.

## II.7 Система токенов

**Источник значений — [tokens.md](tokens.md).** Там полная выгрузка системы
Linear: цвета, шкала шрифтов, отступы, скругления, тени, поверхности,
готовые блоки для `:root` и `@theme` Tailwind v4. Ниже — что из неё берётся
и что меняется под наш случай; дублировать значения здесь незачем.

Система подходит по существу: плотный рабочий инструмент, а не витрина.

### Что берём как есть

**Поверхности тёмной темы.** Четыре уровня вместо теней:

| Уровень | Цвет | Назначение |
|----|----|----|
| 0 | `#08090a` | Холст страницы |
| 1 | `#0f1011` | Карточки, боковая панель, шапка |
| 2 | `#161718` | Всплывающие панели, вложенные поверхности |
| 3 | `#23252a` | Наведение, заливка активной строки |

**Шкала серого текста:** `#ffffff` заголовки, `#d0d6e0` основной текст,
`#8a8f98` вторичный, `#62666d` приглушённый. Цветного текста в основном
потоке нет.

**Границы вместо теней:** `#23252a` для обычных, `#383b3f` для контрастных.
Тень применяется только к всплывающим слоям.

**Типографика:** Inter Variable, начертания 400/510/590 — без жирного 700.
Плотный трекинг: −0.011em на 15px, −0.012em на 20–32px.

**Скругления:** три значения на всю систему — 6px кнопки и поля, 12px
карточки, 9999px пилюли. Плюс 4px для полос этапов на шкале.

**Шаг сетки 4px**, плотная компоновка.

### Что меняем и почему

**Акцент.** Кислотный лайм `#e4f222` работает только на почти чёрном.
На белом фоне светлой темы его контраст около 1.2:1 — это провал WCAG 2.1 AA,
которого требует раздел 18 ТЗ, и как цвет текста или заливка кнопки он
непригоден.

Решение: **акцент разный в двух темах**. Токен `--accent` в тёмной теме
получает лайм, в светлой — тёмно-синий из текущей палитры проекта
(`oklch(0.45 0.19 264)`), уже проверенный на контраст. Роль одна, значение
разное — ради этого токены и существуют.

Лайм в светлой теме остаётся допустимым как **заливка под тёмным текстом**
(например, метка «сегодня»), но не как текст и не как фон кнопки со светлой
подписью.

**Цветов больше, чем у Linear.** У Linear один акцент, потому что там цвет не
несёт доменного смысла. У нас несёт: восемь типов этапов, три состояния
хакатона, три статуса регистрации, пять уровней срочности дедлайна. Эта
палитра уже существует в `index.css` и проверена на контраст — она остаётся.

Дисциплина при этом сохраняется: **цвет разрешён только там, где кодирует
состояние**. Полосы этапов, бейджи, засечка дедлайна. Всё прочее — серая
шкала. Декоративного цвета в системе нет.

**Светлая тема — не инверсия.** Механическое переворачивание тёмной палитры
даёт грязный результат: серые Linear подобраны под чёрный холст. Светлая тема
строится своим набором поверхностей от `#ffffff` вниз, с теми же ролями и
проверкой контраста каждой пары.

**Масштаб шрифтов урезается.** У Linear шкала до 72px — это для витрины.
В рабочем интерфейсе верхний размер 20px (раздел II.5), а 24–72px не
используются вовсе. Берётся только нижняя часть шкалы: 12, 13, 14, 15, 20.

**Ширина не ограничивается 1200px.** У Linear это витринная страница по
центру. Шкала должна занимать всю доступную ширину — чем шире, тем
больше времени видно.

**Berkeley Mono не вводится.** Проприетарный шрифт ради идентификаторов не
нужен: моноширинный уместен для UTC-времени и ключей в аудите, и там
достаточно `ui-monospace`.

### Итоговые слои токенов

```
tokens/
  palette.css     сырые значения обеих тем: void, carbon, ash, lime…
  semantic.css    роли: --background, --foreground, --accent, --border
  domain.css      состояния, статусы, типы этапов, срочность
  dark.css        переопределения ролей для тёмной темы
```

Компоненты обращаются **только к семантическим и доменным** токенам.
Прямое обращение к сырому значению вроде `--color-acid-lime` в компоненте
запрещено: именно оно ломает вторую тему.

# Часть III. Конвенция фронтенда

## III.1 Правило одной папки

Основное требование владельца: **одна папка — один компонент**. Папка
называется по компоненту, внутри файлы с фиксированными именами.

```
event-row/
  event-row.tsx          разметка и поведение
  event-row.module.css   стили, если Tailwind не хватает
  index.ts               реэкспорт
```

Импорт снаружи — только через `index.ts`: `@/shared/ui/event-row`.
Внутренние файлы наружу не видны, и папку можно перестраивать, не трогая
потребителей.

**Тесты лежат отдельно, в `tests/`**, а не рядом с компонентом:

```
src/
  shared/ui/data-display/event-row/
    event-row.tsx
    event-row.module.css
    index.ts
  ...
tests/
  shared/ui/data-display/event-row.test.tsx
  features/schedule/model/pack-lanes.test.ts
```

Дерево `tests/` зеркалит `src/`. Так папка компонента остаётся ровно о
компоненте, а весь набор тестов виден одним списком — что при цели 80%
важнее соседства файлов.

Если компонент разросся, он делится на подкомпоненты вложенными папками, а не
файлами рядом:

```
timeline/
  timeline.tsx
  timeline.module.css
  index.ts
  timeline-ruler/
    timeline-ruler.tsx
    timeline-ruler.module.css
    index.ts
  timeline-row/
    ...
```

Порог деления — 250 строк либо появление второго экспортируемого компонента.

## III.2 Стили: Tailwind плюс локальные модули

Здесь принято решение, расходящееся с буквальной формулировкой запроса, и
причина указана явно.

Полный переход на локальные CSS отвергнут: раздел 14.2 ТЗ фиксирует Tailwind и
shadcn/ui поверх Radix, а токены тем живут в `@theme`. Переписать всё на
CSS Modules значит выбросить shadcn (его компоненты приходят с утилитами) и
продублировать палитру. Это ломает и ТЗ, и уже работающий код.

Отдельно зафиксировано возражение против даже частичного ввода модулей: в
репозитории сейчас **ноль** файлов `.module.css`, и добавление второй системы
оформления усложняет соблюдение лимита в 250 строк, а не облегчает.

Возражение принято частично. Модули вводятся **не везде, а по нужде** — и
нужда настоящая: сетка шкалы с вычисляемыми колонками, штриховка полос,
области попадания через псевдоэлементы и анимация приближения утилитами
Tailwind не выражаются. Порог простой: **если это выражается утилитами, оно
пишется утилитами**. Модуль появляется тогда, когда без него получается
строка `style={{...}}` с арифметикой.

**Принято: гибрид.**

* **Tailwind-утилиты** — раскладка, отступы, типографика, цвета из токенов.
  Пишутся в `.tsx` рядом с разметкой.
* **`component-name.module.css` рядом с компонентом** — то, что утилитами
  выражается плохо: сетка шкалы с вычисляемыми колонками, анимации,
  сложные состояния, `::before`/`::after`, контейнерные запросы.
* **Глобальный CSS** остаётся **только** для токенов темы и сброса. Оттуда
  уходит всё остальное.

Разделение `index.css`:

```
src/styles/
  reset.css              нормализация
  tokens/
    palette.css          базовые цвета
    semantic.css         --background, --foreground, --primary…
    domain.css           состояния, статусы, типы этапов
    dark.css             переопределения тёмной темы
  index.css              только @import перечисленного
```

Каждый файл заметно меньше 250 строк, и добавление типа этапа правит один
файл вместо общей свалки.

## III.3 Именование

### Файлы и папки

**Главное правило: имя файла должно быть различимо во вкладке редактора.**
Это не эстетика — это единственная проверка, которую легко применить.

Замер по текущему состоянию:

| Проблема | Сколько |
|----|----|
| Файлов с именем `api.ts` | **11** |
| Файлов с префиксом `admin-` | 8 |
| Файлов с суффиксом `-page.tsx` | 18 |

Одиннадцать вкладок `api.ts` неразличимы вообще: чтобы понять, какая
открыта, надо смотреть на путь или на содержимое. Это и есть тот случай,
когда конвенция нарушена не по вкусу, а по существу.

**Правила:**

1. `kebab-case` везде, в файлах и папках.
2. **Имя файла уникально в пределах слоя.** Если имя повторяется, к нему
   добавляется предметная область: не `api.ts`, а `hackathon.queries.ts`.
3. **Суффикс типа не дублирует путь.** В папке `features/` файл уже
   очевидно экран — `-page` избыточен. В `entities/event/` префикс
   `event-` избыточен, кроме случая правила 2.
4. **`admin` — не часть имени, а папка.** Это факт маршрута и роли, а не
   свойство компонента. Восемь префиксов `admin-` схлопываются в один
   уровень вложенности.
5. **Один файл — одна сущность.** Множественное число в имени файла
   запрещено: `password-pages.tsx` внутри содержит два разных экрана.

**Точки в имени** отделяют роль файла от предмета: `hackathon.queries.ts`,
`hackathon.types.ts`, `pack-tracks.test.ts`. Читается слева направо — сначала
о чём, потом что это.

| Было | Стало | Почему |
|----|----|----|
| `modules/hackathons/api.ts` | `entities/event/event.queries.ts` | 11 одинаковых имён |
| `modules/timeline/api.ts` | `entities/schedule/schedule.queries.ts` | то же |
| `modules/audit/api.ts` | `entities/audit/audit.queries.ts` | то же |

| `modules/hackathons/my-hackathons-page.tsx` | `features/event-list/my/event-list.tsx` | то же |
| `modules/auth/password-pages.tsx` | `features/password-reset/request/` + `.../confirm/` | множественное число, два экрана |
| `modules/timeline/timeline.tsx` | `features/schedule/schedule.tsx` | `Timeline` — имя системы, не экрана |

| `mocks/db.ts` | `mocks/fixtures/` (разделить, 514 строк) | `db` — запрещённое сокращение и крупнейший файл |

### Что делать со `shared/lib`

Отдельный вопрос, потому что правило запрещает свалки, а `lib` — свалка по
смыслу, пусть слово и не в списке запрещённых. Внутри лежат `batch.ts`,
`cn.ts`, `datetime.ts`, `enums.ts`, `form.ts` и два хука.

**Решение: `shared/lib` расформировывается** по назначению:

| Было | Стало |
|----|----|
| `lib/cn.ts` | `shared/styling/class-names/` |
| `lib/datetime.ts` | `shared/datetime/` |
| `lib/form.ts` | `shared/forms/` |
| `lib/batch.ts` | `shared/api/batch-result/` |
| `lib/enums.ts` | `entities/*/` — это доменные подписи, им не место в `shared` |
| `lib/use-*.ts` | `shared/hooks/` |

`enums.ts` уезжает в `entities` не для порядка: `shared` по определению не
знает о домене, а подписи состояний хакатона — это домен. Сейчас правило
слоёв нарушено именно здесь.

### Символы в коде

| Сущность | Правило | Пример |
|----|----|----|
| Компонент | `PascalCase`, существительное | `HackathonRow` |
| Хук | `use` + существительное | `useHackathonList` |
| Обработчик события | `handle` + предмет | `handleStatusChange` |
| Проп-колбэк | `on` + предмет | `onStatusChange` |
| Булев | `is` / `has` / `can` | `isArchived`, `canPublish` |
| Константа | `SCREAMING_SNAKE_CASE` | `DEADLINE_WARNING_DAYS` |
| Тип и интерфейс | `PascalCase` без префикса `I` | `HackathonSummary` |
| Функция запроса | `use` + сущность + действие | `useHackathonsQuery`, `usePublishHackathonMutation` |

Экспорты именованные. Default-экспорт запрещён, кроме требуемых Vite точек
входа — это правило уже действует глобально и здесь только фиксируется.

### Запреты

* Слова `utils`, `helpers`, `common`, `misc`, `data`, `stuff` в именах папок:
  они не описывают содержимое и превращаются в свалку.
* Множественное число в имени файла компонента: файл содержит один компонент.
* Сокращения: `cn`, `db`, `req`, `btn`. Исключения — общепринятые `id`, `url`,
  `api`, `csrf`.

## III.3a Инструменты для работы над интерфейсом

При работе над фронтендом **обязательно задействовать доступные навыки,
плагины и MCP-серверы**, а не писать вёрстку с нуля по памяти. Требование
владельца, вносится в план, чтобы не забылось.

| Инструмент | Когда применять |
|----|----|
| `impeccable` | Основной. Проектирование и доводка интерфейса: иерархия, когнитивная нагрузка, доступность, отзывчивость, темы, микровзаимодействия, тексты, крайние состояния. Живая правка в браузере |
| `frontend-design` | Художественное направление, типографика, уход от шаблонного вида |
| `ui-ux-pro-max` | Палитры, пары шрифтов, руководства по UX, пресеты анимации, типы графиков |
| `ui-ux-pro-max:ui-styling` | shadcn/ui поверх Radix, Tailwind, тёмная тема — ровно наш стек |
| `ui-ux-pro-max:design-system` | Трёхслойная архитектура токенов: базовые → семантические → компонентные. Прямо ложится на раздел II.7 |
| `dataviz` | Любые графики и показатели: статистика участия, доска состояния очереди |
| `artifact-diagramming` | Схемы для документации |
| `context7` MCP | Актуальная документация библиотек: Tailwind v4, TanStack, Radix, d3-scale, i18next |
| `playwright` MCP | Проверка вёрстки в живом браузере, снимки экрана, e2e |

Порядок применения при новом экране:

1. `context7` — свериться с текущим API библиотек, а не с памятью;
2. `impeccable` или `frontend-design` — решить, как экран устроен;
3. реализация по конвенции этого документа;
4. `playwright` — посмотреть глазами, проверить обе темы и оба языка.

Отдельно: **проверять обе темы и оба языка на каждом экране**. Русский текст
в среднем на 15–20% длиннее английского, и раскладка, собранная под
английский, ломается на русском.

## III.3b Движение

Длительности и кривые — такие же токены, как цвета, и живут рядом с ними.

| Что | Длительность | Свойства |
|----|----|----|
| Наведение, фокус | 100 мс | Фон, тень |
| Выпадающий список, подсказка | 140 мс вход / 100 выход | Прозрачность, сдвиг 4px |
| Диалог | 200 / 140 мс | Прозрачность, масштаб 0.96 → 1 |
| Боковая панель | 240 мс | Сдвиг по X |
| Всплывающее сообщение | 200 / 140 мс | Сдвиг по Y, прозрачность |
| Приближение шкалы | 260 мс | Область значений |
| Переход к сегодня | 320 мс | Прокрутка |

**Выход всегда примерно на треть быстрее входа**: уходить с глаз медленно
раздражает.

### Что не анимируется

* Появление строк после фильтрации — мгновенно. Ступенчатое появление сорока
  строк делает фильтр **медленнее** на ощупь. Самая частая ошибка «красивого»
  интерфейса;
* смена чисел в счётчиках;
* переходы между административными страницами: анимация добавляет 200 мс
  задержки к каждому переходу и не даёт ничего;
* первая отрисовка страницы;
* линия «сегодня».

### Уважение к настройке уменьшенного движения

Одно глобальное правило с `!important` — тот редкий случай, когда он уместен:
это настройка доступности пользователя, и перебивать её не должно ничто.
Плюс отдельная проверка в коде для анимаций, которые идут мимо CSS.

Тонкость: «уменьшить» не значит «убрать». Растворение помогает
ориентироваться, убирать надо перемещение и масштабирование.

## III.3c Производительность

**Разделение сборки по ролям, а не только по маршрутам.** Дефект I.9c:
сейчас участник грузит весь административный интерфейс. Отдельные части:
общая оболочка, участник, администратор, движок шкалы, таблицы.

Ориентиры: начальная загрузка меньше 160 КБ сжатого, крупнейшая отложенная
часть меньше 90 КБ. Проверка размера в CI, падающая при росте больше чем на
десятую — именно она удерживает планку, а не благие намерения.

**Кэш запросов настраивается по типу данных**, а не одним значением на всё:

| Данные | Свежесть |
|----|----|
| Справочники (типы этапов, каналы) | Бессрочно: в пределах сессии не меняются |
| Профиль, сессия | 5 минут |
| Списки и шкала | 30–60 секунд |
| Статус регистрации | 0: пользователь его меняет |
| Журнал аудита | 0: только добавление |

Отдельно: обновление при возврате на вкладку глобально выключено, но **для
статуса регистрации и состояния уведомлений включено**. Вернуться к вкладке
через час и увидеть устаревший статус дедлайна — ровно та беда, ради
предотвращения которой продукт существует.

**Фабрика ключей запросов** вместо строк по месту: тогда сброс кэша
переживает переименования и гарантированно задевает все связанные запросы.

**Шрифты своим хостингом, с подрезкой под кириллицу и латиницу.** Полный
файл Inter — около 110 КБ, подрезанные наборы — примерно 24 и 18 КБ. Это
больше, чем даёт большинство работ над кодом.

**Аватары рисуются из инициалов**: цвет из хеша идентификатора, буквы из
имени. Ноль запросов, ноль скачков вёрстки, работает без сети.

## III.3d Взаимодействие

**Реестр горячих клавиш со стопкой областей**, а не слушатель в каждом
компоненте. Диалог кладёт исключительную область и перекрывает всё, кроме
`Escape` — одно это правило убирает целый класс ошибок «сочетание сработало
при открытом окне».

Тот же реестр служит источником для справки по `?` и для палитры команд:
одно объявление, три места применения.

**Палитра команд** — на существующем диалоге Radix, без новой зависимости.
Обязательно с учётом кириллицы, и отдельно приятная мелочь: сопоставление
раскладки, чтобы набранное `[frfnjy` находило «хакатон».

**Оптимистичные обновления — точечно.** Единственный бесспорный случай:
участник отмечает свою регистрацию. Это главный жест продукта, он обязан
быть мгновенным.

Не делать оптимистичными: создание хакатона, публикацию, пакетные операции —
там частичный отказ норма, и сервер проверяет переходы.

Обязательно отменять запросы в полёте перед оптимистичной записью: иначе
ответ, пришедший следом, откатит изменение. Это ошибка номер один в таких
обновлениях.

**Частичный отказ пакетной операции** нельзя показывать одним словом.
Соглашения API возвращают построчный результат, значит и сообщение
построчное: «Назначено 7 из 10, три не удалось — показать», с диалогом
причин и кнопкой «повторить неудавшиеся». Сообщение об отказе не гаснет само.

**Отмена вместо подтверждения.** Полная история действий — избыточность;
нужно отменить последнее удаление. Всплывающее сообщение с кнопкой на
восемь секунд. Заодно исчезают диалоги подтверждения, и работа ускоряется,
оставаясь безопаснее.

**Скелет против крутилки** — правило без места для суждения:

| Условие | Что показываем |
|----|----|
| Ответ быстрее 200 мс | Ничего |
| Известная форма, первая загрузка | Скелет по реальной раскладке |
| Форма неизвестна | Крутилка, но не раньше 400 мс |
| Повторный запрос уже видимых данных | Старые данные приглушённо |
| Отправка формы | Кнопка с индикатором, без перекрытия экрана |

Скелет, однажды показанный, держится минимум 300 мс — иначе мигание.

## III.4 Слои

Текущее деление `app / modules / shared` уплощено: `modules` содержит и
экраны, и переиспользуемые куски, и обращения к API. Вводится четыре слоя со
строгим направлением зависимостей.

```
app/        оболочка, маршруты, провайдеры
  ↓

## III.5 Наведение порядка в `shared/ui`

Плоские 19 файлов делятся по природе, каждый компонент — своя папка.

```

  primitives/     button, input, textarea, label, checkbox, switch, badge, spinner
  overlays/       dialog, confirm-dialog, popover, tooltip

Составные компоненты (`table` с шестью экспортами, `dialog` с восемью)

бессмысленны в отрыве от корня**. Такие файлы держат подкомпоненты рядом с
корневым и не превышают 250 строк.

## III2.2 Комментарии удаляются, а не переводятся

Отдельно, потому что соблазн велик: комментарий на русском **не переводится
на английский** — он удаляется. Правило CLAUDE.md — ноль комментариев,
и перевод 1808 строк дал бы 1808 английских комментариев вместо нуля.

Это относится и к docstring-ам Go: владелец подтвердил буквальный ноль.
Ссылки на разделы ТЗ, которые в них жили, переезжают в таблицу трассировки
в `docs/`.

Исключение — конфигурационные файлы (`.golangci.yml`, CI, `Makefile`) и
`docs/`: там комментарии допустимы и остаются на русском.

## III2.3 Логи

Сообщения `slog` — английские, всегда:

```
slog.ErrorContext(ctx, "reconciliation pass failed", "error", err)
slog.InfoContext(ctx, "reconciliation created notifications",
    "scanned", n, "primary", p, "reminder", r, "overdue", o)
```

Логи читает не пользователь, а тот, кто чинит систему в три часа ночи, — и
он ищет по подстроке, грепает и гуглит текст ошибки. Русский текст в логах
ломает всё три. Раздел 18 ТЗ требует структурированных логов с `request_id`;
язык там не оговорён, и английский ему не противоречит.

## III2.3a Где лежат словари: два разных случая

Формулировка «русский только в словарях» неполна: словарей **два комплекта**,
в разных местах, и путать их нельзя.

| | Backend | Frontend |
|----|----|----|
| Что | Письма, Telegram-сообщения | Весь интерфейс, тексты ошибок |
| Кто отрисовывает | Worker, фоновый процесс | Браузер |
| Когда | В момент создания уведомления | В момент показа экрана |
| Язык берётся из | Профиля получателя | Текущей локали пользователя |
| Путь | `backend/internal/locale/messages/` | `frontend/src/shared/i18n/locales/` |

**Почему тексты писем не могут жить на фронтенде.** Уведомление отправляет
worker — отдельный процесс без браузера. Раздел 9.6 ТЗ требует неизменяемый
снимок `payload_json` на момент создания, а часть IV.3 добавляет к нему язык
получателя. Фронтенд в этой цепочке не участвует вообще: к моменту, когда
пользователь откроет экран, письмо уже отправлено.

Поэтому в `backend/internal/locale/` допустимы ровно эти ключи:

* `notification.*` — тексты уведомлений о событиях;
* `email.*` — письма подтверждения, восстановления, приглашения;
* `duration.*` — склонения для подстановки в них («2 дня», «5 дней»).

**И ничего больше.** Всё, что видит пользователь на экране, живёт во
frontend. Если в backend-словаре появился ключ вида `error.*`, `button.*`,
`page.*` — это ошибка: такой текст обязан отдаваться кодом и переводиться
клиентом (раздел III2.4).

Проверяется тестом: множество префиксов ключей backend-словаря ограничено
тремя перечисленными.

## III2.4 Ошибки, доходящие до пользователя

Соглашения API уже устроены правильно: в ответе есть машинный `code` и
человекочитаемый `message`. Отсюда деление:

| Часть | Язык | Кто отдаёт |
|----|----|----|
| `code` | Английский, стабильный идентификатор | Сервер |
| `message` в ответе | Английский | Сервер, как запасной вариант |
| Текст на экране | По локали пользователя | Клиент, по `code` из словаря |

**Сервер не угадывает язык клиента.** Он отдаёт `code`, а клиент находит по
нему строку в своём словаре. Английский `message` в ответе остаётся как
запасной вариант для тех, кто читает API напрямую, и для случая, когда код
неизвестен клиенту.

Значит словарей на каждый язык два комплекта, и один из них — зеркало
серверных кодов:

```
src/shared/i18n/locales/
  en/errors.json    ключи = коды ошибок API
  ru/errors.json    то же, по-русски
```

Полнота проверяется тестом: множество ключей в словаре ошибок совпадает с
множеством кодов, которые умеет отдавать сервер. Иначе появится код без
перевода, и пользователь увидит английскую строку посреди русского экрана.

Раздел 9.6 ТЗ: «Язык продуктовых сообщений MVP — русский». Соглашения API:

# Часть IV. Локализация

## IV.1 Расхождение с ТЗ

Раздел 14.2 ТЗ: «библиотеки i18n — язык интерфейса и сообщений один, русский».
Требование двух языков это решение отменяет. Правка ТЗ обязательна: раздел
14.2, раздел 9.6 (язык уведомлений) и приложение C (язык по умолчанию).

## IV.2 Решение

Формат хранения — JSON, по требованию владельца.

```
src/shared/i18n/
  locales/
    ru/
      common.json
      hackathon.json
      registration.json
      notification.json
      auth.json
    en/
      … те же файлы
```

Деление по доменам, а не один файл на язык: словарь на весь продукт вылетит
за 250 строк на первой сотне строк интерфейса.

Ключи структурные, не текстовые: `hackathon.state.upcoming`, а не
`«Предстоящий»`. Текстовый ключ ломается при правке русской формулировки и
не переводится.

Библиотека — `i18next` с `react-i18next`: поддержка множественного числа
(«3 участника» / «5 участников»), интерполяция, ленивая загрузка словарей.
Русский требует трёх форм множественного числа, самописный словарь это
воспроизведёт плохо.

### Переключатель языка

Русский и английский, переключаются в любой момент из шапки и из профиля.
Смена мгновенная, без перезагрузки — словари загружены или подгружаются
лениво.

Определение языка при первом входе: `users.locale` для авторизованного,
иначе `localStorage`, иначе `navigator.language`, иначе русский.

Язык хранится в профиле пользователя (`users.locale`) — переносится между
устройствами — и в `localStorage` для неавторизованных.

### Что придётся локализовать помимо строк

Не только тексты. Иначе получится наполовину переведённый интерфейс:

* **Даты и время.** `date-fns` уже в стеке и имеет локали. Формат
  различается: «27 августа 2026» против «27 August 2026», порядок дня и
  месяца, 24-часовой формат против 12-часового.
* **Множественное число.** Русский требует трёх форм («1 участник»,
  «2 участника», «5 участников»), английский двух. Это причина брать
  `i18next`, а не писать словарь руками.
* **Относительное время.** «через 3 дня», «просрочено на 2 часа» — на шкале
  срочности это основной способ подачи.
* **Названия месяцев на шкале** — линейка переводится вместе с
  интерфейсом.
* **Порядок сортировки** списков по названию: русский и латиница
  сортируются разными правилами, нужен `Intl.Collator` с текущей локалью.

### Что не переводится

Пользовательские данные: названия хакатонов, описания, `team_role`,
административные заметки. Они вводятся администратором на своём языке и
хранятся как есть. Многоязычные названия хакатонов — это отдельная модель
данных, и в текущий объём она не входит.

## IV.3 Что остаётся русским

Уведомления Telegram и email — по языку **получателя**, а не отправителя.
Это меняет `payload_json` из раздела 9.6 ТЗ: снимок должен содержать язык, на
котором сформирован. Иначе смена языка после создания уведомления даст текст
на языке, которого пользователь уже не выбирает.

Сообщения об ошибках API остаются с машинным `code`
([api-conventions.md](api-conventions.md)), а `message` локализуется на
клиенте по коду. Сервер не должен угадывать язык клиента.

# Часть IVa0. Личный слой

## Главное архитектурное решение этого документа

Сегодня система **административная**. Администратор заводит хакатон,
назначает участника, настраивает напоминания. У участника ровно один глагол:
«я зарегистрировался». Всё в `hackathon_participants`, `registrations`,
`notification_rules` принадлежит администратору.

Но почти всё, что делает продукт живым — заметки, чек-листы, закладки,
артефакты сдачи, история участия — принадлежит **участнику**. Это другая
поверхность с другой моделью владения.

**Решение: явно разделить два слоя.**

| | Административный слой | Личный слой |
|----|----|----|
| Владелец | Администратор | Участник |
| Видимость | Общая | Своя, кроме явно расшаренного |
| Аудит | `audit_log`, неизменяемый | Не аудируется |
| Гарантии | Транзакции, версии, дедупликация | Дешёвая запись, можно удалять |
| Примеры | Хакатон, этап, назначение, правило | Заметка, задача, закладка, артефакт |

Смешивать их нельзя, и вот почему конкретно:

* **Личные напоминания не идут в таблицу `notifications`.** У неё
  обязательный `registration_status_id`, версионируемый `logical_key`,
  триггер запрета удаления и самая тонкая логика в проекте (AC-NOTIF-01…19).
  Личная задача не имеет статуса регистрации и не нуждается в
  дедупликации по версиям. Ей нужен более слабый механизм — шина событий из
  [realtime-notifications.md](realtime-notifications.md).
* **Личные записи не идут в `audit_log`.** Он неизменяем триггером и
  предназначен для административных действий. Автосохранение заметки залило
  бы его мусором.

Это то же рассуждение, которым в парном документе событие парсера было
вынесено из домена уведомлений. Один раз сформулировано — применяется везде.

## Честность формулировок

Ключевая оговорка ТЗ — система не проверяет внешний сайт — это **не
ограничение, а позиция продукта**. TickTick не проверяет, вынесли ли вы
мусор. Ценность в структуре и напоминании, а не в верификации.

Следствие для текстов интерфейса: везде «вы отметили», «по вашим словам» —
и никогда «подтверждено», «проверено». Это пункт код-ревью, а не разовая
правка.

Запрещены и смягчённые версии того же: «вероятно зарегистрирован», отметка
«последний раз проверено», любая шкала уверенности. Всё это создаёт
впечатление проверки, которой нет.

# Часть IVa. Ссылки на ресурсы

## IVa.1 Проблема

Сейчас ссылок в модели три и все одиночные: `Hackathon.website_url`,
`Stage.url`, `Registration.url`. У живого хакатона их десяток: правила,
чат участников, форма сдачи, критерии судейства, датасет, документация API,
запись на менторов, страница результатов.

Складывать их в `description` текстом — то, от чего продукт должен уводить.

## IVa.2 Модель

Отдельная сущность `resource_link`, привязанная к хакатону или к этапу.

| Поле | Назначение |
|----|----|
| `id` | UUID |
| `hackathon_id` | FK, обязателен |
| `stage_id` | nullable FK: ссылка уровня этапа, а не хакатона |
| `kind` | тип ссылки, см. ниже |
| `url` | HTTPS |
| `title` | подпись; при пустой берётся из `kind` |
| `is_pinned` | закреплена в карточке |
| `sort_order` | порядок в списке |
| `created_at` / `updated_at` | UTC |

Ссылка уровня этапа появляется на шкале при наведении на полосу — форма
сдачи нужна ровно во время этапа сдачи, а не всё время.

## IVa.3 Типы ссылок

Типизация, а не свободный список: тип даёт значок, группировку и понятный
порядок. Набор закрытый, расширяется миграцией.

| Тип | Что это |
|----|----|
| `WEBSITE` | Сайт хакатона |
| `RULES` | Правила и регламент |
| `REGISTRATION` | Форма регистрации — уже есть в `Registration.url` |
| `SUBMISSION` | Форма сдачи работы |
| `CHAT` | Telegram, Discord, Slack участников |
| `DATASET` | Данные для задачи |
| `API_DOCS` | Документация предоставленного API |
| `JUDGING` | Критерии оценки |
| `MENTORS` | Запись к менторам |
| `RESULTS` | Страница результатов |
| `SPONSOR` | Партнёры |
| `OTHER` | Прочее |

`REGISTRATION` намеренно дублирует `Registration.url`, но не заменяет её:
каноническая ссылка регистрации остаётся в `Registration`, потому что она
участвует в версионировании уведомлений
(`notification_content_version`, раздел 7 ТЗ). Ссылка типа `REGISTRATION`
в этом списке — только отображение той же величины, отдельно она не
редактируется.

## IVa.3a Ссылка может быть любой, не только HTTPS

Сейчас схема требует HTTPS в трёх местах, и это лишнее ограничение:

| Где | Ограничение |
|----|----|
| `000002_events.up.sql:19` | `events_website_https` |
| `000002_events.up.sql:53` | `stages_url_https` |
| `000003_participation.up.sql:51` | `registrations_url_https` |
| `services/validate.go:69` | Валидатор с тем же правилом |

Плюс ТЗ: разделы 5.1, 5.2 и 7 описывают эти поля как «HTTPS URL».

**Принято: ограничение снимается.** Причина простая — оно не защищает ни от
чего, а мешает по-настоящему. Система по ссылкам не ходит (это позиция
раздела IVa.4), значит безопасность соединения её вообще не касается: ссылку
открывает браузер пользователя, и это его дело. При этом реальные страницы
хакатонов регулярно живут на `http`, на внутренних адресах, в Telegram
(`tg://`) и в документах — и сейчас такую ссылку просто невозможно сохранить.

Что остаётся вместо `CHECK` на префикс:

* **Проверка на разбираемость.** Строка должна быть похожа на адрес, а не
  быть произвольным текстом. Проверяется в коде, не в базе.
* **Запрет опасных схем.** `javascript:`, `data:`, `vbscript:` не
  сохраняются: такая «ссылка», подставленная администратором в `href`,
  выполняется в браузере другого пользователя. Это единственная проверка
  схемы, которая осмысленна.
* **`rel="noopener noreferrer"` и `target="_blank"`** на всех внешних
  ссылках в интерфейсе.
* **Отметка в интерфейсе, если ссылка не HTTPS** — значок, а не запрет.
  Пользователь решает сам.

Требует правки ТЗ разделов 5.1, 5.2 и 7 — внесено в таблицу части VIIIa.

## IVa.4 Что не делаем

**Не ходим по ссылкам за метаданными.** Соблазн подтянуть заголовок
страницы и значок сайта велик, но это исходящие запросы к произвольным
адресам с сервера — и подделка ссылки становится способом заставить сервер
постучаться куда угодно. Значок берётся по типу ссылки, заголовок вводит
администратор.

Это же согласуется с принципиальной позицией ТЗ: система не ходит на внешний
сайт и ничего там не проверяет.

# Часть IVb. Профиль и настройки

## IVb.1 Экран настроек

Отдельный раздел, а не диалог: настроек слишком много для всплывающего окна.
Разделы слева, содержимое справа.

| Раздел | Содержимое |
|----|----|
| Профиль | Имя, аватар, о себе, ссылки |
| Аккаунт | Email, смена пароля, смена почты |
| Внешний вид | Тема (светлая / тёмная / системная), язык (RU / EN), плотность |
| Уведомления | Канал по умолчанию, привязка Telegram, настройки по типам событий |
| Сессии | Активные входы, завершение сессий |
| Опасная зона | Деактивация и удаление аккаунта |

Тема и язык дублируются в шапке быстрым переключателем: это то, что меняют
на ходу, а не заходя в настройки.

## IVb.2 Поля профиля

Расширение `users`. Сейчас там `display_name`, `email`, `telegram_username`,
`telegram_chat_id`, `preferred_channel`.

| Поле | Зачем |
|----|----|
| `avatar_url` | Узнавание в списках участников |
| `bio` | Короткое описание |
| `github_url` | Основная ссылка для этой аудитории |
| `website_url` | Портфолио или личный сайт |
| `locale` | RU / EN |
| `theme` | LIGHT / DARK / SYSTEM |
| `timezone` | Отображение времени; сейчас жёстко Europe/Moscow |

**Личная таймзона** — заметное улучшение: раздел 9.6 ТЗ фиксирует системную
Europe/Moscow, и для международного хакатона это неверно. Хранение остаётся
в UTC, меняется только отображение. Требует правки ТЗ.

## IVb.3 Как не превратить настройки в чулан

Правило: **поле попадает в профиль, только если продукт его где-то
показывает или использует**. Размер футболки и пищевые ограничения кажутся
уместными для хакатона, но пока их некому передавать — организатор о нашей
системе не знает. До появления такого получателя они не заводятся.

Ссылки на соцсети множатся бесконечно. Берутся две, значимые для аудитории:
GitHub и произвольный сайт. Остальное — при явном запросе.

## IVb.4 Настройка уведомлений

Матрица «тип события × канал», а не один общий выключатель:

| Событие | Telegram | Email | В приложении (зеркало) |
|----|----|----|----|
| Напоминание о дедлайне | ✓ | ✓ | ✓ |
| Просрочка регистрации | ✓ | ✓ | ✓ |
| Назначение на хакатон | | ✓ | ✓ |
| Системные события (админ) | | | ✓ |

**Третий столбец — не канал.** Это принципиально, иначе документ противоречит
парному: в [realtime-notifications.md](realtime-notifications.md) отдельно
разобрано, почему `IN_APP` не становится каналом. Раздел 10 пункт 4 ТЗ
определяет доступность канала через `telegram_chat_id` и подтверждённый
email; у отображения в приложении такого условия нет, оно доступно всегда,
пока `User.is_active`. Стоит ему попасть в цепочку выбора — и `UNDELIVERABLE`
для него недостижим, а сценарий AC-NOTIF-05 перестаёт воспроизводиться.

Поэтому столбец «в приложении» **не участвует в выборе канала по разделу 10
и не влияет на `UNDELIVERABLE`**. `models.Channel` остаётся из двух значений.

Ограничение касается только первых двух столбцов: если пользователь отключил
и Telegram, и email, уведомление становится `UNDELIVERABLE`, а не пропадает
молча.

# Часть IVb2. Разбор внешних идей

Идеи из отдельного списка «Идеи для улучшения ТЗ». Разобраны по существу:
что берём, что уже есть, что берём в изменённом виде и что не берём.

## Берём как есть

**Экран «Что горит».** Главная страница входа: ближайшие дедлайны,
незавершённые регистрации, стартующие события — всё в одном месте. Это
недостающий ответ на вопрос «что от меня требуется прямо сейчас», и он
сильнее любого списка. Ставится входной страницей вместо списка событий.

**Фильтр «требует моего действия».** Показывает только то, где от участника
действительно чего-то ждут: `TODO` при активной регистрации, неархивное
опубликованное событие. Не отдельный экран, а вид в боковой панели и режим
экрана «что горит».

**Прогресс регистрации команды** — «4 из 5 зарегистрировались» на карточке
события. Дёшево (одна агрегация), а социальное давление работает лучше
напоминаний. Осторожность: показывать **числа, а не имена отстающих** —
публичный список «кто не сделал» превращает инструмент в доносчика.

**Быстрые действия на карточке**: «я зарегистрировался», «открыть форму»,
«открыть сайт» — без захода внутрь. Прямо ложится на закреплённые ссылки
из части IVa.

**Сортировка по срочности по умолчанию.** Ближайшие дедлайны сверху.
Параметр `sort` в запросе, состояние в URL.

**Скрыть завершённые.** Переключатель «только активные»: `UPCOMING` +
`ACTIVE`. Уже наполовину есть — раздел 11 ТЗ прячет архивные по умолчанию, —
но завершённые сейчас показываются вперемешку с идущими.

**История уведомлений** — «мои уведомления»: дата, тип, канал, краткий текст.
Пользователь видит, что система работала, и может проверить, не потерялось ли
письмо. Read-only выборка из `notifications` по `recipient_user_id`.

Важная оговорка: **показывать превью, а не `payload_json` целиком**.
Раздел 4 ТЗ чистит payload через 90 дней, и экран обязан переживать пустое
поле, а не падать на старых записях.

**Подсказки на статусах.** «TODO — требуется отметка о регистрации»,
«NOT_REQUIRED — регистрация не требуется». Снимает путаницу у новичков.
Тексты берутся из локализации, не вшиваются.

**Статистика администратора** на списке событий: сколько в каждом статусе,
доля покрытия регистрацией, число просроченных. Кэш на 5 минут — данные
меняются медленно, а агрегация по всем событиям недешёвая.

## Уже в плане

| Идея | Где |
|----|----|
| Обратный отсчёт до дедлайна | IVd.3 |
| Визуальные состояния дедлайна | II.5, шкала срочности |
| Личные заметки к событию | IVc.2 |
| Лента календаря iCalendar | IVd.1 |
| Предпросмотр массовых изменений | Соглашения API, парный endpoint `/preview` |

## Берём в изменённом виде

**Цветовое кодирование статуса — но не только цветом.** Предложение:
красный при просрочке, жёлтый при дедлайне ближе трёх дней, зелёный при
`DONE` или `NOT_REQUIRED`.

Смысл верный, но в чистом виде это повторяет нарушение WCAG 1.4.1 из
раздела I.9b — цвет становится единственным носителем смысла. Берём **шкалу
срочности из раздела II.5** (пять уровней, а не три) и обязательно с
дублирующим признаком: значок плюс текст «осталось 2 дня» / «просрочен на 1
день».

Отдельно: **зелёный для `NOT_REQUIRED` неверен**. `DONE` и `NOT_REQUIRED` —
разные вещи: первое значит «я сделал», второе — «меня освободили». Красить их
одинаково значит стирать различие, которое раздел 8 ТЗ вводит намеренно.
`NOT_REQUIRED` — нейтральный серый, а не успех.

**Три дня как порог «жёлтого»** заменяются на шкалу раздела II.5: больше
недели — спокойно, 1–7 дней — внимание, меньше суток — срочно, после
дедлайна — просрочка. Три дня попадают в середину и отдельным порогом не
нужны.

## Не берём

**«Вычисляемое поле» для цвета статуса.** Формулировка предполагает поле в
модели или в ответе API. Срочность **вычисляется на клиенте от текущего
времени**: она меняется каждую минуту, и хранить её значит либо пересчитывать
строки по расписанию, либо отдавать устаревшее значение. Раздел 8 ТЗ знает
только `TODO`, `DONE`, `NOT_REQUIRED`, и добавлять «просрочено» в статус
нельзя — это состояние отображения, а не домена.

# Часть IVc. Личные возможности участника

Всё в этой части относится к личному слою (часть IVa0): свои таблицы,
владелец — участник, без аудита, с правом удаления.

## IVc.1 Личный чек-лист по хакатону — недостающий глагол

Сегодня участник умеет ровно одно действие: перевести статус в DONE.
Реальное участие — это два десятка мелких обязательств: подать тезисы,
поставить SDK, забронировать гостиницу, записать демо, сделать репозиторий
публичным, залить слайды.

```
participant_tasks
  id, hackathon_id, user_id
  title, notes
  due_at      nullable
  stage_id    nullable
  done_at     nullable
  sort_order
```

Это то самое ощущение TickTick, ради которого затевалась переделка, и
единственное, что заставит открывать приложение во вторник, когда до
хакатона ещё неделя.

**Напоминания по этим задачам идут через шину событий**, а не через
`notifications`. Обоснование в части IVa0. Раздел 21 ТЗ прямо относит
«напоминания по произвольным дедлайнам вне Registration» к решениям после
MVP — здесь они появляются, но по отдельному, более слабому механизму.

### Шаблоны чек-листов — обязательны вместе с задачами

Пустой список задач — смерть любой такой функции. Поэтому вместе с ней идут
готовые наборы: «подготовка», «день сборки», «день сдачи», плюс свои
сохранённые. Кнопка «применить шаблон» превращает пустой экран в десять
осмысленных пунктов.

**Не выпускать чек-лист без шаблонов.**

## IVc.2 Заметки по хакатону

Одно поле Markdown на пару «пользователь + хакатон». Автосохранение,
отрисовка Markdown. Всё.

Огромная польза при копеечной цене: черновик во время хакатона ведут все, и
держать его рядом с дедлайнами и ссылками значит, что он найдётся потом.

**Ловушка:** тяга сделать «как в Notion» — блоки, вложенные страницы,
совместное редактирование — очень сильна и съест месяцы. Одно поле.

## IVc.3 Артефакты сдачи

Что именно сдано: ссылка на репозиторий, видео демо, слайды, живой стенд,
страница сдачи, строка описания. Плюс самоотчётная отметка «сдал».

Две выгоды. Сейчас — предсдаточная проверка, которая предотвращает
классическую катастрофу «забыли открыть репозиторий». Потом — материал для
истории участия: без сохранённых артефактов ей нечего показывать.

Формулировки честные: «я сдал», а не «сдача подтверждена».

## IVc.4 Результат и история участия

Самоотчётный итог: место, приз, трек, заметка. Важная деталь: должно
одинаково нормально записываться и «второе место в треке ИИ», и просто
«участвовал». Большинство хакатонов не заканчиваются призом, и инструмент,
который умеет записывать только победы, делает нормальный случай похожим на
неудачу.

Поверх этого — **история участия**: сколько хакатонов, в каких ролях, с
какими результатами и артефактами. Это то, что удерживает пользователя
после события: трекер без памяти — календарь, трекер с памятью — личная
летопись.

Стоит дёшево, потому что это модель чтения над уже собранными данными.

## IVc.5 Ретроспектива

Три вопроса через два дня после конца хакатона: что получилось, что нет,
что в следующий раз. Ценно для тех, кто ходит на хакатоны регулярно.

**Работает только вместе с напоминанием.** Никто не пойдёт заполнять
ретроспективу по своей воле — нужен толчок. Без напоминания не делать.

## IVc.6 Закладки в каталоге

«Интересно, но пока не участвую» — отдельно от `hackathon_participants`,
который означает административное назначение и включает уведомления.

**Выпускать одновременно с каталогом, а не после.** Каталог, в котором
нечего сохранить, — тупик: посмотрел и закрыл.

# Часть IVd. Время и внимание

Это сильная сторона продукта: инфраструктура планировщика и worker уже есть
и обкатана. Расширять здесь дёшево и полезно.

## IVd.1 Подписка календаря (ICS)

Персональная ссылка с секретным ключом, отдающая ленту всех дат: хакатоны,
этапы, дедлайны. Подписался один раз в Google, Apple или Outlook — дальше
обновляется само.

**Лучшее соотношение пользы к затратам во всём документе.** Пользователь
получает интеграцию с календарём, которым уже пользуется: без OAuth, без
квот, без состояния синхронизации. Один endpoint и проверенная библиотека.

Двусторонняя синхронизация с Google Calendar отвергнута: OAuth, обновление
токенов, квоты, сверка состояния, разрешение конфликтов, распространение
удалений и постоянная эксплуатационная нагрузка — на порядок больше работы
ради малой добавки к ленте, которую можно только читать.

**Важно по безопасности:** вся авторизация в системе — cookie плюс
`X-CSRF-Token`, а календарный клиент ни того, ни другого не умеет. Значит
endpoint работает по неугадываемому токену в адресе и исключается из
CSRF-проверки явно. Это надо описать, иначе кто-нибудь потом «починит»
исключение.

### Модель угроз ленты календаря

Endpoint по построению неаутентифицированный и отдаёт всё расписание
человека. Одного упоминания токена мало:

| Вопрос | Решение |
|----|----|
| Энтропия | Не менее 128 бит случайности |
| Хранение | Только хеш, как `refresh_token_hash` в миграции идентификации |
| Отзыв | Кнопка перевыпуска в настройках |
| Деактивация пользователя | **Токен отзывается вместе с сессиями.** Раздел 3 ТЗ отзывает при деактивации все `Session`, но лента — не сессия, и без явного правила деактивированный человек продолжит получать расписание. Ровно та ошибка, которую парный документ поймал для WebSocket |
| Удаление аккаунта | Токен удаляется |
| Частота | Ограничение обязательно: календарные клиенты опрашивают ленту каждые несколько минут, бессрочно и без участия человека |
| Логи | Токен лежит в адресе и попадёт в журнал обратного прокси на каждый опрос. Раздел 18 ТЗ запрещает токены в логах — нужна явная вычистка этого сегмента пути в конфигурации nginx |

## IVd.2 Сводка «что на этой неделе»

Письмо или сообщение раз в неделю: все ближайшие дедлайны, этапы и личные
задачи по всем хакатонам сразу. Пустая сводка не отправляется.

Сегодня уведомления привязаны к одному дедлайну одной регистрации — узко и
реактивно. Сводка — **единственное представление, которое делает участие в
нескольких хакатонах осмысленным**.

Новых доменных сущностей не требует: задача worker плюс настройка
периодичности. Идёт через шину событий, не через `notifications`.

## IVd.3 Обратный отсчёт

Живой отсчёт до ближайшего дедлайна с меняющейся дробностью: дни → часы →
минуты. Дёшево, а срочность передаёт так, как статичная дата не умеет.
Зрительный пульс продукта.

## IVd.4 Пересечения и конфликты

Отметка, когда два хакатона накладываются по времени или два дедлайна
попадают в одни сутки.

Новых таблиц не нужно — запрос по назначениям с проверкой пересечения
интервалов, в PostgreSQL это одна строка на диапазонах.

**Это то, чего не скажет календарь**: он не знает, что эти события
трудозатратны. Продукт знает и обязательства, и их тяжесть.

Подаётся как наблюдение, не как запрет: иногда пересечение — осознанный
выбор.

**Отдельно про предупреждения о перегрузке.** Соблазн написать «у вас три
хакатона за месяц, вы выгорите» велик, но инструмент, который поучает,
выключают. Показывать наблюдение, а вывод оставлять пользователю. И уж точно
не слать это в уведомления.

## IVd.5 Личная таймзона — не украшение, а фундамент

Раздел 9.6 ТЗ фиксирует системную Europe/Moscow, а раздел 21 относит
пользовательские таймзоны к решениям после MVP. Это надо пересмотреть.

**Неверно показанный дедлайн — единственная ошибка, которая необратимо
уничтожает доверие к трекеру дедлайнов.** Для международного хакатона
московское время просто неверно.

Хранение остаётся в UTC, идентификаторы зон — IANA, не смещения. У каждой
абсолютной отметки времени подпись зоны; у дедлайна показываются оба
времени, когда они расходятся.

Это условие корректности для ICS, сводки и отсчёта: лента календаря с
неправильными зонами хуже отсутствующей, потому что ошибается молча.

## V.1 Линтер

`golangci-lint` отсутствует. Вводится `backend/.golangci.yml`:

* `dupl` — дубли, поддерживает DRY.

Запуск в `make lint` и в CI наравне с Biome.

## V.2 Архитектура и SOLID

Слои `controllers → services → repositories → models` уже разделены и это
сильная сторона проекта. Проблема в другом — размер и ответственность.

**`auth_service.go`, 495 строк** — регистрация, вход, refresh, подтверждение
почты, сброс пароля, смена почты. Шесть причин для изменения в одном типе,
нарушение принципа единственной ответственности. Деление:

```
services/auth/
  registration_service.go    регистрация и подтверждение
  session_service.go         вход, refresh, отзыв
  password_service.go        сброс и смена пароля
  email_change_service.go    смена адреса
```

**`registration_controller.go`, 469 строк** — контроллер регистрации, правил
и статусов сразу. Делится по трём ресурсам, которыми управляет.

**Интерфейсы объявляются потребителем, а не поставщиком.** Сейчас
`DeliveryService` принимает `TelegramSender` и `EmailSender` — это правильно
и распространяется на репозитории: сервис объявляет узкий интерфейс с теми
методами, что ему нужны, вместо зависимости от конкретного типа репозитория.
Это принцип разделения интерфейсов и заодно то, что делает сервисы
тестируемыми без базы.

Про OOP отдельно: Go — не язык классов, и насаждать наследование в нём вредно.
Приложимы композиция, инкапсуляция за интерфейсами и внедрение зависимостей —
они уже применяются. Это и есть корректное прочтение SOLID для Go.

## V.3 Комментарии

Правило владельца — ноль комментариев. Оговорка: комментарии вида
`// Notification — запись очереди доставки (раздел 9.2 ТЗ)` являются
docstring-ами публичного API Go, их требует `revive` и по ним строится
`go doc`.

**Принято: удалить поясняющие комментарии внутри тел функций** — они
объясняют «как», что должно быть видно из кода. **Оставить одну строку
docstring** на экспортируемом типе и функции, где она содержит ссылку на
раздел ТЗ: эта ссылка — единственная нить между кодом и источником истины, и
восстановить её из кода невозможно.

Комментарии в SQL-миграциях остаются: они объясняют неочевидные приёмы
(денормализованный `hackathon_end_at`, слоты `slot_no`), которые
[CLAUDE.md](../CLAUDE.md) прямо велит не менять походя.

Если владелец настаивает на буквальном нуле — правило применяется и к
docstring-ам, но тогда ссылки на разделы ТЗ переносятся в отдельную таблицу
трассировки в `docs/`, иначе связь теряется.

## VI.1 Отправная точка

## VI.2 Пороги

Frontend, `vitest.config.ts`:

```
coverage: {
  provider: 'v8',
  thresholds: { lines: 80, functions: 80, branches: 75, statements: 80 },
  exclude: ['**/*.gen.*', 'src/mocks/**', 'src/test/**', '**/index.ts'],
}
```

Backend: `go test -coverprofile` с проверкой порога в CI. Исключаются `cmd/`
и генерируемое.

Пороги ставятся **сразу**, но с текущими значениями. Порог 80% на репозитории
с пятью тестами уронит CI в первый же день и будет отключён — известный
способ похоронить требование.

**Механика — храповик:** порог равен достигнутому и никогда не опускается.
Каждый PR либо держит уровень, либо поднимает его. Так 80% достигается без
дня, когда сборка красная у всех.

**80% не везде одинаково полезны.** Высокая планка ставится там, где тест
ловит настоящие ошибки: `shared/lib`, `shared/api`, `model/`-слой шкалы,
доменные сервисы Go. Экранные компоненты покрываются не построчно, а
десятком сквозных сценариев Playwright.

Иначе получаются тесты, написанные ради числа: отрисовали компонент,
убедились, что не упал. Это отрицательная ценность — время CI, поддержка и
ложная уверенность. Приёмочные сценарии QA-01…QA-07 из
[tasks.md](tasks.md) стоят больше любого процента.

## VI.3 Приоритет

Покрытие 80% как самоцель бессмысленно: 80% геттеров не стоят одного теста
дедупликации. Порядок по риску:

1. **Домен уведомлений** (QA-01, QA-04) — самое сложное и полностью
   непокрытое: конкурентный планировщик, версии, отмена во время отправки,
   переключение каналов, восстановление аренды. Сценарии AC-NOTIF-01…19 уже
   написаны в разделе 19 ТЗ — их надо перенести в тесты дословно.
2. **Права и IDOR** (QA-03, AC-AUTHZ-01) — политика `403`/`404`, CSRF,
   ограничение частоты, отзыв сессий.
3. **Переходы состояний** — раздел 16 ТЗ таблицей, каждая строка есть тест.
4. **Frontend**: `entities` (запросы, преобразования) и `shared/ui`, затем
   экраны через MSW.
5. **E2E Playwright** (QA-05) — путь «создать → опубликовать → назначить →
   отметить регистрацию → остановить напоминания».

# Часть VIII. Порядок работ

Разбито на этапы, каждый оставляет репозиторий в рабочем состоянии. Правило
[CLAUDE.md](../CLAUDE.md) сохраняется: следующий этап не начинается, пока
`make verify` не проходит.

## VIII.0− Объём и что делать, если времени нет

Честная оценка: в плане около шестидесяти шагов, среди них переименование
модуля Go, перестройка всего дерева фронтенда, две локали, новая предметная
область (география и каталог), переписанный главный экран, разделение
backend-сервисов, покрытие тестами с пяти файлов до 80% и реальное время.
Для одного разработчика с агентом — [dependency-order.md](dependency-order.md)
раздел 2 исходит именно из этого — это **месяцы, а не спринт**.

Поэтому порядок урезания задаётся заранее, пока решение не принимается в
спешке.

**Если делается только три этапа — 0б, 1 и 5а.** Срочные исправления снимают
нарушение доступности и вхолостую работающую мемоизацию; токены дают обе
темы; шкала — то, ради чего продукт затевался. Всё остальное можно отложить,
не потеряв продукт.

**Порядок отказа, от первого к последнему:** реальное время (этап 8) →
каталог и география (этап 4) → перестройка структуры (этап 2) → локализация
(этап 3). Перестройка структуры отложена намеренно: она ничего не даёт
пользователю и полезна только при продолжении работы.

**Что не откладывается ни при каких условиях:** этап 0б (доступность и
ошибки), тесты прав перед этапом 6 и умолчание `Europe/Moscow` при вводе
таймзоны.

## VIII.0 Правила механических этапов

Этапы 0 и 2 переставляют файлы массово: переименование модуля Go задевает
каждый импорт, перестройка фронтенда двигает всё дерево. Без дисциплины
`git log --follow` и `git blame` перестают работать навсегда.

1. **Сначала коммит только с перемещениями** — `git mv`, ни одной правки
   содержимого. Тогда Git распознаёт переименование и история сохраняется.
2. **Потом отдельный коммит с содержимым.** Смешение убивает распознавание.
3. **Файл `.git-blame-ignore-revs`** с хешами обоих массовых коммитов плюс
   `git config blame.ignoreRevsFile` — иначе `blame` во всём репозитории
   покажет одного автора и одну дату.
4. **Переименование модуля Go — через `go mod edit` и `gofmt -r`**, не через
   `sed`: замена по тексту заденет строки и комментарии.
5. **Каждый механический этап — на короткой ветке**, вливается целиком.
   Наполовину сделанный перенос дерева откатить нельзя.
6. **Метка на каждый завершённый этап.** Это единственный способ вернуться,
   когда следующий этап пошёл не так.

## VIII.0a Порядок тестов относительно переделок

Правило [dependency-order.md](dependency-order.md) раздел 5 и CLAUDE.md:
задача готова только вместе с тестами её приёмочных сценариев.

Отсюда следует то, что легко нарушить: **тесты прав и аутентификации пишутся
до разделения `auth_service.go`, а не после.** Сейчас на 495 строк auth
приходятся два теста, и ни один не покрывает вход. Разделить этот файл на
четыре сервиса без покрытия — значит менять самую чувствительную часть
системы вслепую.

| Что | Когда |
|----|----|
| QA-03, AC-AUTHZ-01: права, IDOR, CSRF, отзыв сессий | **До** этапа 6 |
| QA-01, QA-04, AC-NOTIF-01…19: домен уведомлений | **До** этапа 8 |

Утверждение этапа 2 «тесты обязаны проходить без правок» при пяти тестовых

## VIII.0b Миграции данных

У всех новых полей есть существующие строки, и умолчания надо назвать
заранее. Отдельно: CLAUDE.md требует пары `.up.sql` / `.down.sql` для каждой
миграции.

| Поле | Умолчание для существующих строк |
|----|----|
| `hackathons.event_kind` | `HACKATHON` |
| `hackathons.scope` | Решается вместе с вопросом из части IX. Пока не решён — миграцию писать нельзя |
| `hackathons.format` | Nullable: формат прошлых хакатонов неизвестен, выдумывать его нельзя |
| `hackathons.country_code`, `city` | Nullable |
| `users.locale` | `ru` — сохраняет текущее поведение |
| `users.theme` | `SYSTEM` |
| `users.timezone` | **`Europe/Moscow`, обязательно.** Иначе при выкладке у всех разъедется отображение дедлайнов — та самая ошибка, которую раздел IVd.5 называет необратимо разрушающей доверие |
| `notifications.payload_json` | Язык существующих снимков проставляется как `ru`, иначе worker не отрисует старые записи |

**Что делают виды с пустым `scope`.** Если `scope` nullable, то `scope IN
(RU, GLOBAL)` и `scope IN (INTL, GLOBAL)` не покажут ни одной старой строки:
все существующие хакатоны окажутся видны только в виде «Все». Это молчаливая
пропажа данных из интерфейса, и её надо либо принять сознательно, либо
заполнить поле при миграции.

# Часть IX. Открытые вопросы

* **Почасовая сетка в календаре.** Нужна ли зона часов под многодневными
  полосами, как в календаре TickTick. Сейчас у этапа только дни, но
  контрольная точка внутри дня («сдача в 18:00») в такой сетке была бы
  нагляднее. Требует уточнения.
* **Самозапись в каталоге.** Действие «участвую» противоречит разделу 6 ТЗ,
  где участников назначает только администратор. Либо каталог даёт лишь
  «хочу участвовать» как заявку администратору, либо ТЗ меняется и вводится
  самостоятельное присоединение. Второе — заметное расширение модели прав.
* **Кто наполняет каталог до появления парсера.** Если только администратор
  вручную, каталог первое время будет пустым, и смысл второй страницы
  теряется. Возможно, её стоит включать одновременно с парсером.
* `scope` заполняется вручную администратором или выводится парсером при
  импорте — от этого зависит, обязательное поле или nullable.
* Митапы включаются в MVP или только подготавливается модель.
* Буквальный ноль комментариев или сохранение docstring со ссылками на ТЗ
  (раздел V.3).
* Нужна ли панель деталей на ширине 1024px — минимум по разделу 18 ТЗ, где
  три панели по 240 + 380 оставляют списку 400px.
* Язык уведомления берётся из профиля получателя на момент создания снимка —
  подтвердить при правке раздела 9.6 ТЗ.
