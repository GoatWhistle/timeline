- [x] **Б1.** Каталог — **только авторизованным**. Снимает расхождения с ТЗ

      `format` (`ONLINE`/`OFFLINE`/`HYBRID`, NOT NULL) + `country_code`
      (обязателен при офлайне и гибриде, для гибрида — страна финала);
      `origin` (`RU`/`WORLD`, NOT NULL, умолчание `RU`). Виды строятся по

      а не полосой — тогда вечернее событие не схлопывается в чёрточку при

- [x] **Б6.** **Митапы делаются сразу**, прайм-версия. `kind` в той же
      таблице. **`hackathon` → `event` во всей системе**: таблица, 17 внешних

      называется половина строк, — закреплённая ложь. Слово «хакатон»
      остаётся только там, где речь о виде `kind = HACKATHON`

**Миграции разрешено править**, а не только добавлять новые — поля
географии вносятся прямо в `000002_hackathons.up.sql`, отдельная миграция и

## Время и внимание

Личная таймзона (пункты 124–127) — предусловие корректности для всех четырёх
оставшихся пунктов: лента календаря и отсчёт с неправильной зоной ошибаются
молча. Она закрыта, поэтому пункты ниже разблокированы по существу.

- [x] **137.** Лента ICS по секретному токену. Таблица
      `calendar_feed_tokens` (только хеш, один активный токен на человека,
      каскад при удалении), сервис с выдачей и ротацией, контроллер,
      маршруты, отзыв при деактивации и при удалении, вычистка токена из
      логов приложения и `nginx.conf`. Приёмочные тесты написаны и проверены
      мутациями: `calendarfeed`, `calendarsecret`, `calendarstore`,
      `calendarlog` в `internal/controllers/authz`, `calendar_ics_test.go` в
      `internal/services`, `scrub_test.go` в `internal/controllers/httpx`.
      Доказано: отозванный токен (через `DELETE` и через ротацию) не отдаёт
      ленту, чужой токен не отдаёт ни чужого события, ни административной
      заметки, деактивированный владелец получает `404` даже если строка
      токена жива, неизвестный/отозванный/деактивированный/некорректный дают
      побайтово одинаковый ответ, в базе лежит только SHA-256, токен не
      попадает ни в один из трёх вызовов `ScrubPath`, ограничение частоты
      работает без учётной записи. Круговой обход миграции `000012`
      (`up → down → up`) проверен, инварианты БД — частичный уникальный
      индекс, `CHECK` на длину хеша и `ON DELETE CASCADE` — тоже.
      **Оговорка:** формат ICS проверен разбором (развёртка, экранирование,
      `UID`, `DTSTAMP`/`DTSTART`/`DTEND`, UTC), а не подпиской настоящего
      календарного клиента — этого в тестах нет и это стоит сделать руками
      перед выпуском
- [x] **138.** Модель угроз ленты: 128 бит (на деле 256 — `NewSecret` даёт
      32 случайных байта), хранение хешем, отзыв,
      **отзыв при деактивации**, ограничение частоты, вычистка токена из
      логов nginx (раздел 18 ТЗ запрещает токены в логах). Неотделимо от 137:
      это не проверка после реализации, а её условия. Каждое условие закрыто
      тестом, каждый тест убит мутацией соответствующей защиты. Обнаружено и
      исправлено попутно: связка не была подключена в `internal/cli` —
      `container.go` не создавал ни репозиторий, ни сервис, `serve.go` не
      передавал ни `CalendarFeeds`, ни лимиты, поэтому в работающем
      приложении маршрут отвечал бы паникой, а отзыв при деактивации молча
      не срабатывал
- [x] **139.** Сводка «что на этой неделе», пустая не отправляется.
      **Место выбрано по инвариантам, а не по удобству: шина раздела 9.9, а не
      `notifications`.** У сводки нет `registration_status_id`, объявленного
      `NOT NULL` (она охватывает много регистраций сразу либо ни одной), а
      `notification_type` закрыт `CHECK` из трёх значений — строка в очереди
      потребовала бы править `CHECK` применённой миграции. `logical_key` тоже
      не подходит: его версии по разделу 9.3 выводятся из одной порождающей
      сущности, а сводка — про промежуток времени. Отсюда `WEEKLY_DIGEST` с
      `audience_kind = USER` и `dedup_key = weekly-digest:{user_id}:{понедельник
      недели в зоне получателя}`. **Пустая не создаётся вовсе** — это правило
      пункта, и оно проверено отдельным тестом плюс мутацией. Границы недели,
      язык и время — в зоне и на языке получателя (пункты 91д–91з, 124–127),
      снимком на момент создания. Раздел 9.9.2a ТЗ, миграции не потребовалось
- [x] **140.** Обратный отсчёт с меняющейся дробностью: дни → часы → минуты →
      секунды, частота тика подстраивается под дробность, чтобы не будить
      React каждую секунду ради надписи «осталось 4 дня». Момент дедлайна и
      всё после него — «срок прошёл», отсчёт назад не ведётся
- [x] **141.** Пересечения событий и близкие дедлайны — **наблюдение, не
      запрет**: строка «Наблюдение: N пар событий пересекаются по времени».
      Ни предупреждений о выгорании, ни запретов, и **не в уведомления** —
      вывод остаётся за пользователем. Дедлайны группируются по дню
      **в личной таймзоне**: в другой зоне те же две отметки могут разъехаться
      по разным суткам, поэтому без пункта 126 признак был бы неверным

# Правила, действующие постоянно

Не задачи, а условия приёмки каждой из них.

- [ ] **П1.** Оба языка и обе темы проверяются на каждом экране
- [ ] **П2.** Цвет никогда не единственный признак состояния
- [ ] **П3.** Формулировки честные: «вы отметили», не «подтверждено»
- [ ] **П4.** Личные записи не идут в `notifications` и `audit_log`
- [ ] **П5.** Контракт в OpenAPI пишется до реализации
- [ ] **П6.** Изменение, требующее правки ТЗ, вносится в таблицу части VIIIa
      в тот же момент, когда предлагается
- [ ] **П7.** Механические этапы: `git mv` отдельным коммитом, метка после
- [ ] **П8.** Новый endpoint получает ограничение частоты сразу
- [ ] **П11.** Сочетания клавиш переназначаемые: раскладки по системам,
      готовые наборы (Vim и прочие), свои наборы. **Не сейчас** — раздел
      III.3c1 плана, но реестр строится с расчётом на это
- [ ] **П9.** При работе над интерфейсом **обязательно** задействуются `impeccable`,
      `frontend-design`, `ui-ux-pro-max`, `context7`, `playwright`
- [ ] **П10.** `make verify` проходит до перехода к следующей задаче

# Если времени нет

Порядок урезания задан заранее, чтобы не решать в спешке.

**Минимум из трёх этапов: 0б, 1, 5а.** Срочные исправления снимают нарушение
доступности и холостую мемоизацию, токены дают обе темы, шкала — то, ради
чего продукт затевался.

**Порядок отказа:** реальное время → каталог и география → перестройка
структуры → локализация.

**Не откладывается никогда:** этап 0б, тесты прав перед этапом 6, умолчание
`Europe/Moscow` при вводе таймзоны.
